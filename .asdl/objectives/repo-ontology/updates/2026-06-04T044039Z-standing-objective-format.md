# Standing Objective Format

## Summary

Converted `repo-ontology` to the standing Objective format and simplified its durable goal.

The standing goal is to keep `CONTEXT.md`, `CONTEXT-MAP.md`, and docs maintained through `grill-with-docs` up to date with current checked-in repo reality. The Objective no longer frames ontology work as a finite sweep with goal-met completion; the remaining phase list is current backlog/history under the standing maintenance direction.

After the first `objective-next` preview, the Runner Policy wording was refined to avoid `Materialization` / `side effects` jargon. Future previews should say plainly which files or areas may change, how the work will be left, and what will not happen unless explicitly requested.

The policy was then sharpened so `objective-next` recommends exactly one action route. Implementation is appropriate only from a concrete, source-backed plan; if the roadmap row or current evidence is still too broad, `objective-next` should ask a yes/no confirmation question so the user can type `yes` to start planning/readback work, then present the proper plan. Manual slices should use a confirmed steered planning session and should not present immediate implementation as an option.

## Objective Impact

- `objective.md`: simplified the thesis around keeping domain-language documentation current, replaced finite completion criteria with standing retirement semantics, and added lightweight Definition of Progress / Runner Policy boundaries; later refined the Runner Policy to use plain preview wording instead of `Materialization` / `side effects` jargon, require one recommended action route, require implementation to proceed from a concrete source-backed plan, and require a yes/no confirmation step before plan-first sessions.
- `roadmap.md`: added a standing `[~]` operating direction for keeping `CONTEXT.md`, `CONTEXT-MAP.md`, and `grill-with-docs`-maintained docs up to date, then refined its policy note to use the same yes/no plan-first confirmation routing.
- Future `objective-next` invocations may offer confirmed docs/context execution when the slice is source-backed and within policy; terminology decisions, context-surface changes, and non-obvious ambiguities still require steering first.
