# Repo Ontology and CONTEXT-MAP

## Thesis

The asdl monorepo has rich domain language in the root Objective-system context, across 8 in-scope Python workspace packages, and now in the repo-local TypeScript/Pi extension package. One Python package, the multi-subpackage `asdl-core`, is itself several subdomains. The Clinkr H2 section of `packages/asdl-core/CONTEXT.md` (commit `8de0a295`) showed that the `grill-with-docs` skill produces high-signal glossaries; the ongoing improvement is to run the same workflow across the repo-level context and every package or extension surface with meaningful domain language, then tie them together with a root `CONTEXT-MAP.md`.

The outcome: a contributor or agent landing on the repo can navigate the asdl ontology from a single entry point, with cross-context naming collisions (Review/Comment/Feedback, State/status variants, active/root status, branch/ref/plan usage, and evidence/finding language) explicitly flagged rather than buried in source. The Phase 0 scaffold was correct as an initial slice, but the repo has since gained `packagechk` as a standalone workspace package, substantial checked-in Pi extension workflows under `ts/packages/pi-extensions/`, Objective archive/unarchive mechanics, the `roaster` rename of the former `asdl-reviewer` package, and the `aretro` retrospective-evidence package; the Objective therefore includes rebaselines as live repo language lands.

## Scope

A whole-repo grilling and documentation sweep, sequenced bottom-up by dependency depth so vocabulary established earlier flows into later sessions:

- Phase 0 — Scaffold `/CONTEXT-MAP.md` with a planned-contexts list and initial explicit skips. This landed before the current package inventory settled.
- Phase 0.5 — Rebaseline `/CONTEXT-MAP.md` against current ground truth: index the existing root `CONTEXT.md`, add `packagechk` as an in-scope standalone package context, keep `asdl-dispatcher` out of scope as a tracked CLI stub, and stop treating `asdl-initiatives` as a package skip because no tracked package exists.
- Phase 0.6 — Rebaseline after Pi/Objective workflow drift: update root Objective language for active/archive roots and `objective archive`, add the TypeScript/Pi extension context for `@asdl/pi-extensions`, refresh map relationships/ambiguities, and update adjacent Objective/Pi docs that had become contradictory.
- Phase 0.7 — Rebaseline after roaster/aretro inventory drift: treat `roaster` as the renamed review harness package, add `aretro` as an in-scope retrospective-evidence package, and refresh `/CONTEXT-MAP.md` relationships/ambiguities before more per-package sessions proceed.
- Phase 1 — Finish and refresh `packages/asdl-core/CONTEXT.md` by appending H2 sections for `Git`, `Gt`, `Gh`, `Top-level utilities`, and `Sessions` alongside the existing `Clinkr` section, and by reconciling any per-subpackage context splits.
- Phase 2 — Create `packages/brmem/CONTEXT.md`. brmem is a foundational Branch Memory primitive used by repo-local skills and agent workflows; landing its vocabulary first lets later sessions reference it canonically without implying package-level consumers.
- Phase 3 — Create per-package `CONTEXT.md` for `asdl-pr-address`, `roaster`, `asdl-slots`, `asdl-objectives`, `packagechk`, and `aretro`. `asdl-pr-address`, `roaster`, `asdl-slots`, and `asdl-objectives` are peer asdl plugin packages; `packagechk` is a standalone package-name CLI; `aretro` is a standalone skill-facing retrospective evidence CLI that depends on `asdl-core` session/git/clinkr vocabulary. `@asdl/pi-extensions` is handled by Phase 0.6 because its implementation and docs already landed before the Python package sessions completed.
- Phase 4 — Finalize `/CONTEXT-MAP.md`: populate the Relationships section with concrete cross-package import/runtime edges discovered during sessions, explicitly record standalone/no-edge contexts, and add a top-level "Flagged ambiguities" section for cross-context naming collisions.

Each phase is one or more focused grilling sessions driven by `.claude/skills/grill-with-docs`, conducted across separate user turns. The Objective spans multiple grilling/readback sessions plus periodic ground-truth rebaselines and the Phase 4 finalize pass.

## Non-Goals

- Do not split `asdl-core` into per-subpackage `CONTEXT.md` files. Keep it as a single file with H2 sections; revisit only if a labs subpackage graduates.
- Do not create `CONTEXT.md` for `asdl-dispatcher` while it remains a tracked CLI stub with no live operations. Do not recreate or reserve a `CONTEXT.md` for `asdl-initiatives`; no tracked package exists in the current workspace. Do not recreate or reserve an `asdl-reviewer` context; the tracked package identity is now `roaster`.
- Do not produce ADRs unless the `grill-with-docs` three-criteria bar fires (hard to reverse, surprising without context, real trade-off). Expect 0–2 ADRs total across all sessions.
- Do not edit production Python or TypeScript implementation code as part of this Objective. The work is documentation/ontology only.
- Do not auto-generate glossaries from source or AST analysis. The value is in human-led grilling that surfaces ambiguity and forces canonical choices.
- Do not introduce a documentation generator, lint check, or CI gate for `CONTEXT.md` shape. The skill's format is the contract; enforcement is human review.

## Completion Criteria

- `/CONTEXT-MAP.md` exists at repo root, links the existing root `CONTEXT.md`, lists all 8 in-scope Python package contexts (`asdl-core`, `brmem`, `asdl-pr-address`, `roaster`, `asdl-slots`, `asdl-objectives`, `packagechk`, and `aretro`) plus the repo-local `@asdl/pi-extensions` context with active links as they exist, includes an explicit "Out of scope" note for `asdl-dispatcher`, and does not describe `asdl-initiatives` or `asdl-reviewer` as tracked packages unless the map is explicitly noting their absence or rename history.
- `/CONTEXT-MAP.md` contains a populated Relationships section reflecting real import edges discoverable from `pyproject.toml` or source, including explicit standalone/no-`asdl-core` status where that is the ground truth (for example `packagechk`).
- `CONTEXT.md` and `docs/objective-system.md` distinguish Active Objective Root, Objective Archive Root, Objective Close, Objective Archive, and Closure Marker without treating archive state as closure state.
- `packages/asdl-core/CONTEXT.md` remains the single asdl-core context file and contains H2 sections for `Clinkr`, `Git`, `Gt`, `Gh`, `Top-level utilities`, and `Sessions`. Each section follows the Clinkr pattern: Language entries with `Avoid:` aliases, followed by Relationships. Any competing asdl-core subpackage context split must be reconciled rather than left as a parallel glossary.
- `ts/packages/pi-extensions/CONTEXT.md` exists with Language and Relationships sections for project-local Pi extension adapters, engineered package behavior, planned branches, checkpoint/new-branch flows, runner subagents, and terminal presentation.
- Each of `packages/brmem/CONTEXT.md`, `packages/asdl-pr-address/CONTEXT.md`, `packages/roaster/CONTEXT.md`, `packages/asdl-slots/CONTEXT.md`, `packages/asdl-objectives/CONTEXT.md`, `packages/packagechk/CONTEXT.md`, and `packages/aretro/CONTEXT.md` exists with Language and Relationships sections.
- Cross-context naming collisions surfaced during sessions (the "Review" overload across `gh` / `pr-address` / `roaster`, "Comment" usage across `gh` / `pr-address` / `roaster`, "State/status" usage across `gh`, `format.state_badge`, Objectives, slots, and `packagechk.CheckStatus`, active/root status, branch/ref usage across `git`/`gt`/`slots`/`brmem`/`aretro`, plan terminology across Objectives / planned branches / Branch Memory, and evidence/finding language across Objectives / `aretro` / `roaster`) are either resolved identically across files or recorded in the map's "Flagged ambiguities" section.
- Readback test: an unfamiliar contributor can open `/CONTEXT-MAP.md`, navigate to any listed context, and explain back its key terms and `Avoid:` aliases without opening the source files.
- Every relationship listed in `/CONTEXT-MAP.md` corresponds to a real import edge or runtime interaction — no speculative connections, and no stale expected edge such as `asdl-objectives → brmem` unless source or runtime evidence later makes it true; `asdl-objectives → asdl-core.gt` is now a known-real edge that must appear.

## Assumptions and Risks

Assumptions:

- The `grill-with-docs` skill's output shape (Language entries with `Avoid:` aliases, Relationships subsection, optional Flagged ambiguities) is the right format. We are not inventing a new convention.
- The context inventory can drift during a multi-session documentation sweep. The current closure target is the root context, 8 in-scope Python package contexts (`asdl-core`, `brmem`, `asdl-pr-address`, `roaster`, `asdl-slots`, `asdl-objectives`, `packagechk`, and `aretro`), and the repo-local `@asdl/pi-extensions` context; if another tracked package or checked-in extension surface with real domain language lands before closure, the map should be rebaselined before more per-context sessions proceed.
- `asdl-core`'s labs subpackages (`clinkr`, `gh`, `git`, `gt`, and `sessions`) will not graduate to standalone packages during this Objective, so keeping them as H2 sections in one file is stable.
- `asdl-dispatcher` remains out of scope while its tracked group has no operations. `asdl-initiatives` is not a tracked package in the current workspace; if it is reintroduced with real implementation, that is a fresh rebaseline signal rather than a standing package skip. `asdl-reviewer` is a historical package identity replaced by `roaster`, not a parallel context slot.
- Bottom-up dependency ordering will let vocabulary established earlier flow forward into later sessions. If a later session forces a rename in an earlier section, those edits are cheap because Markdown is the only artifact.
- A multi-session sweep is acceptable across many user turns; this is not a single-session deliverable. Some sections may also be satisfied by an adjacent Objective that owns the underlying code rather than by a dedicated repo-ontology grilling session — the `## Gh` section landed this way via the pr-gateway-unification Objective (#555/#580). repo-ontology accepts such externally-authored sections when they conform to the section criteria (Language + `Avoid:` aliases + Relationships) rather than re-grilling; the trade-off is that those sections must be re-checked against the criteria rather than assumed conformant.
- The `grill-with-docs` ADR criteria (hard to reverse, surprising, real trade-off) are correctly tuned. Most sessions will produce zero ADRs and that is the expected outcome.

Risks:

- Package/context inventory drift already materialized repeatedly: `packagechk` became a tracked standalone package while `asdl-initiatives` disappeared; later `@asdl/pi-extensions` plus Objective archive mechanics became substantial repo language; now `asdl-reviewer` has been renamed to `roaster` and `aretro` has landed as a tracked retrospective-evidence package. Mitigation: Phase 0.5 and Phase 0.6 rebaselined earlier drift; Phase 0.7 has now rebaselined the map for `roaster`/`aretro` and refreshed relationships/ambiguities before Phase 2/3 package contexts continue.
- Grilling appetite drops mid-sweep, leaving partial `CONTEXT.md` files. Mitigation: each session is self-contained — a partial Objective still leaves correct glossaries for the packages already done, and closure can be deferred without rework on earlier files.
- Cross-context naming collisions discovered late may force edits in earlier files. Mitigation: bottom-up ordering minimizes this; revisiting a closed H2 section is straightforward Markdown editing and does not invalidate the rest of the work. `packagechk` adds at least one candidate collision around status/state terminology.
- The repo's domain language drifts as packages add new concepts after their sessions close. This materialized again before closure: the not-yet-written `asdl-objectives` context gained the opt-in `objective gt` Graphite stack-projection surface and a known-real `asdl-objectives → asdl-core.gt` edge before Phase 3; `aretro` and `asdl-core.sessions` also introduce branch-retrospective evidence vocabulary before the sweep has closed. The Phase 2 brmem context also produced temporary package-local alignment notes; those have now been resolved by aligning Base Namespace copyability, Entry Locator wording, prompt-plugin framing, Namespace ownership wording, and empty Snapshot copy conflicts with the context, then deleting `packages/brmem/FOLLOWUP.md`. Mitigation: ground-truth rebaselines update Phase 1/3/4 so later package/map sessions capture them; future changes after a package session remain closure-note or follow-on material unless they invalidate the map's package inventory or relationship edges, in which case rebaseline before closure.
- Non-Goal conflict surfaced and was resolved in Phase 1: the temporary `asdl_core.gt` context split has been folded into `packages/asdl-core/CONTEXT.md#gt`, and the competing subpackage context file has been deleted. The single-file-H2 policy remains the active asdl-core context boundary.
- A future `asdl-core` subpackage graduation could orphan its H2 section. Mitigation: the graduation process owns splitting the section into its own `CONTEXT.md` as part of the move; not a blocker today.
- "Flagged ambiguities" entries could grow into unresolved-debate noise. Mitigation: each entry is one line and resolved (term: meaning chosen, alternatives listed); never a venue for open argument.
- A grilling session could devolve into source-code archaeology rather than language-sharpening. Mitigation: the skill's `<what-to-do>` block already constrains this — questions one at a time, answered by code lookup when possible, written into `CONTEXT.md` inline as they resolve.

## Open Questions

- Should `/CONTEXT-MAP.md` link into `asdl-core`'s H2 sections individually (e.g. `Clinkr → packages/asdl-core/CONTEXT.md#clinkr`), or treat `asdl-core` as a single linked context? — _Provisional answer at Phase 0 scaffold:_ treat `asdl-core` as one linked context but name each H2 anchor inline next to the link. Revisit at Phase 4 readback if per-anchor naming proves noisy or insufficient.
- When a cross-context ambiguity is severe (e.g. "Review" used differently in `gh`, `pr-address`, and `roaster`), is the right response to canonicalize a single name across packages, or to keep package-local names with the boundary documented?
- Once the sweep is done, what is the maintenance cadence — opportunistic on PRs that touch domain code, or a periodic re-grilling cycle?
