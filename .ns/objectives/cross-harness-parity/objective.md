# Cross-Harness Workflow Parity

## Thesis

This toolkit has been built Pi-native: Pi's JS extension system registers slash commands that run logic directly, with no language-model round trip. Claude Code and Codex have no such extension layer — they reach workflows only through **skills** (markdown `SKILL.md`) that call **CLIs**. The goal is that the Pi extension layer is purely *additive*: deterministic logic lives in a shared CLI usable by every harness, a skill documents the workflow for Claude/Codex, and the Pi extension is a thin ergonomic layer (picker, custom UI, structured tool) on top. What we do not want is workflow logic trapped in TypeScript with no CLI/skill path (a gap), or the same logic re-implemented in two places (duplication).

An audit (2026-06-03) confirmed the architecture already makes this cheap: the CLI→Pi bridge (the Pi host package's CLI command extension, `@ji/pi` at `ts/packages/hosts/pi/`) is generic — any CLI command table becomes Pi slash commands with zero per-command code — and skills are a single on-disk artifact (`skills/<name>/SKILL.md`) consumed identically by Pi (`/skill:<name>`), Claude (`.claude/skills`), and Codex (`.agents/skills`). The gap pattern has since shifted twice. The original audit found **primitives shared, orchestration trapped in the Pi host package**; the orchestration then consolidated into shared, test-backed capability packages. The June-era gap — tested cores with no CLI entry point — has now largely closed for the flow family: the **Flow capability** (`@ji/flow`, `ts/packages/capabilities/flow/`) exposes `ji flow changes|cp|autobranch|branch-latest-commit|autoslot|submit|regenerate-pr|push|land|pull-trunk` as real repo-local CLI commands via the `@ji/kernel` `ji` bin, with Pi `/ji:flow:*` as thin CLI bridges carrying typed parity metadata. What remains trapped is the **cmux dispatch family**: the `@ji/ccc` cmux orchestration (`ts/packages/capabilities/ccc/src/cmux/`) is reachable only through Pi `/ccc:workspace:*` commands — no CLI entry, no skill, no parity metadata. The other open leg is **skill coverage**: wrapper skills exist for only four of the ten flow commands, and the parity doctrine (FULL requires CLI + skill) has not been reconciled with the typed metadata that self-declares all ten `/ji:flow:*` surfaces FULL.

> Naming/relocation rebaseline (2026-07-03, superseding the 2026-06-26 rebaseline): a second workspace-wide rename landed. The npm scope moved `@sdl/*` → `@ji/*`; the `sdl` CLI family was replaced by a single `ji` bin owned by `@ji/kernel` (`ts/packages/kernel/`); repo dirs moved `.sdl` → `.ji` and `sdl.toml` → `ji.toml`. Capability packages live under `ts/packages/capabilities/` (address, aretro, branch-context, ccc, flow, handoff, objective, plans, roaster, slot) and register repo-local `ji <group> <command>` groups through kernel descriptors under `.ji/extensions/`. Other relocations: `@ji/ccc` at `ts/packages/capabilities/ccc/`; `@ji/capability-kit` at `ts/packages/capability-kit/`; the standalone autobranch package was retired and its core absorbed into `@ji/flow` (`ts/packages/capabilities/flow/src/autobranch/`); the land core moved from ccc into `@ji/flow` (`ts/packages/capabilities/flow/src/land/`); model env vars moved `SDL_*` → `JI_*` (`JI_SLUG_MODEL`, `JI_CCC_SIDEBAR_MODEL`, etc.; `PI_DRAFT_MODEL` unchanged); the model-slug seam is `ts/packages/infra/core/src/primitives/model-slug.ts` with a capability-kit-side split at `ts/packages/capability-kit/src/kit/model-slug.ts`. The per-row names in `parity-table.md` are now **two renames** behind (`@asdl`-era rows under a `@sdl`-era stale banner) and await a parity-review full sweep (see Risks).

This Objective is the cross-harness parity **umbrella**. It owns a living parity table (every Pi surface → its parity status), every remaining parity gap, and a durable parity-review workflow that prevents new gaps from landing. The sibling Objectives it previously deferred rows to — `planned-branch-ts-cli` and `asdl-dev-submit-consolidation` — are both closed; their delivered rows are folded into the table here and the umbrella now owns all remaining gaps directly.

The former standalone `command-output-summaries` Objective is subsumed here as a parity-native shared primitive workstream. It is not a Pi-surface row yet because no Pi command exists; the work is tracked here so the first summarized-command implementation is a shared CLI/helper with skill guidance before any optional Pi adapter appears.

## Scope

- Maintain a living **parity table** (`parity-table.md` in this Objective directory) classifying every Pi extension command as FULL / PARTIAL / NONE / WAIVED parity, with the shared CLI backing and the driving skill per row. Pi tool calls are host-native bridges and do not require their own parity metadata rows; selected non-tool UI primitives may remain recorded when this Objective explicitly tracks them. The table was seeded from the 2026-06-03 audit and last fully swept 2026-06-10. Keeping it current is part of this Objective's tracking discipline (see below); the table's per-row names are now two workspace renames stale (`@asdl`→`@sdl`→`@ji`) and need a full sweep.
- Close the remaining **orphan orchestration** gap: the cmux dispatch family. A CLI taking explicit inputs (plan path, prompt) over the `@ji/ccc` cmux modules (`ts/packages/capabilities/ccc/src/cmux/`: `dispatch-from-trunk.ts`, `dispatch-prompt.ts`, `slot-dispatch-plan.ts`, `slot-open-branch.ts`) and the shared `@ji/capability-kit` cmux utilities (`focused-terminal-tab.ts`, plus ccc's `prompt-file.ts`), with an agent-neutral launch path; covering `/ccc:workspace:dispatch-plan` (and its `/ccc:surface:dispatch-plan` variant), `/ccc:workspace:dispatch-prompt`, and the thin `/ccc:workspace:open-branch` pairing. Pi keeps only session-history "latest plan" resolution. These surfaces currently also lack typed parity metadata.
- Finish the **flow-family parity legs**: `ji flow land|push|autoslot|changes|pull-trunk|regenerate-pr` exist as shared CLI commands with Pi `/ji:flow:*` bridges, but no wrapper skill drives them (skills exist only for `autobranch`, `branch-latest-commit`, `cp`, `submit` as `sdl-flow-*`). Either author the missing skills or make an explicit doctrine decision that a kernel-CLI command with a typed-metadata FULL declaration is Claude/Codex-reachable without a wrapper skill, and record that decision in the parity table rules.
- Sustain the **parity-review discipline**: the `parity-review` route of the `code-workflows` skill runs diff-scoped review (flagging any added/changed Pi command lacking a CLI+skill counterpart or a recorded waiver) and on-demand full-repo sweeps that refresh the parity table. Tool-call surfaces such as `dispatch_runner_subagent` and grill UI tools are treated as Pi-native host bridges; dependent workflows should still document an agent-neutral fallback when they rely on those tools.
- Own the former `command-output-summaries` workstream as a parity-native shared primitive: define and implement a harness-neutral summarized-command CLI/helper that writes full stdout, stderr, and combined logs to payload artifacts, returns bounded deterministic summaries, exposes explicit command/cwd/timeout semantics, supports generic/test/lint/typecheck profiles, and provides skill guidance plus optional Pi adapter without making Pi canonical.

Delivered scope, kept as context rather than live work: the Flow capability's CLI push-down (the entire `ji flow` group with Pi `/ji:flow:*` CLI bridges and typed FULL metadata, including the unified land command covering both single-PR and stack landing); `autobranch` (core in `@ji/flow`, `ji flow autobranch` CLI, `sdl-flow-autobranch` skill, Pi bridged); the checkpoint/submit/branch-latest-commit wrapper skills (`sdl-flow-cp`, `sdl-flow-submit`, `sdl-flow-branch-latest-commit`, renamed from the `code-*` family to mirror the Flow CLI); the `/handoff:list` deduplication onto the handoff capability CLI (now `ji handoff list`); the provider-model-default consolidation behind the `@ji/core` model-defaults seam; and the distributed typed parity gate (per-package `definePiSurfaceParity` metadata with fake-host `*-parity.test.ts` gates across flow, handoff, objective, branch-context, pi core, and local pi-tools). Also historical: `/cp-preview` / `/checkpoint-preview` were removed rather than reconciled, and the former `/code:changes` WAIVED verdict is superseded by the `ji flow changes` CLI.

**Parity table tracking:** `parity-table.md` is the canonical status surface for this Objective. Rules:

- Every Pi extension command appears as exactly one row; Pi tool calls do not require parity rows. Selected non-tool UI primitives may be recorded when the Objective explicitly tracks them.
- A row is **FULL** only when a shared CLI carries the deterministic logic and a skill drives it so Claude/Codex reach the workflow standalone; the Pi part must be purely additive. (Whether a kernel-CLI command with typed FULL metadata but no wrapper skill satisfies this is an open doctrine question — see Open Questions.)
- **WAIVED** rows are genuinely Pi-native primitives whose value *is* the Pi UI/session behavior; they require a documented non-Pi fallback for any dependent workflow.
- The table is refreshed whenever this Objective is updated with parity-relevant findings, and the parity-review workflow's full-sweep mode (the `parity-review` route of the `code-workflows` skill) checks it against live evidence and refreshes it with a Semantic Update when drift is found.
- Shared primitives with no Pi command surface yet do not get parity-table rows until a Pi command exists; this Objective may still track them in roadmap prose when their purpose is to prevent a future parity gap.

## Non-Goals

- Do not aim for identical *UI* across harnesses. Parity means workflow reachability, not pixel/widget equivalence. Pi-native UI (pickers, grill UI, status line) stays Pi-only.
- Do not build the machine-checkable CI parity gate / parity manifest beyond the shipped per-package typed accounting gates in this Objective; broader wiring is parked as a later hardening of the review workflow.
- Do not turn the kernel CLI into a nested command framework beyond the repo-local capability-group mechanism it already has, and do not build a generalized "branch artifacts" CLI above `brmem`.
- Do not add routine validation-only roadmap rows; targeted checks/tests are completion evidence.
- Do not make summarized-command execution a broad bash interceptor, Pi-only runner-subagent feature, or LM-driven summarizer. The default command summary remains deterministic, harness-neutral, and explicit opt-in behavior.

(Historical: this Objective previously declined to re-own the planned-branch and submit workstreams while `planned-branch-ts-cli` and `asdl-dev-submit-consolidation` were open; both siblings are now closed and their delivered rows are folded into the parity table here.)

## Completion Criteria

- Every row in `parity-table.md` is either **FULL** (shared CLI + skill, Pi additive — or per a recorded doctrine decision, shared CLI + typed metadata) or a recorded, justified **WAIVED** primitive with a documented agent-neutral fallback — except any consciously parked rows. No unexplained PARTIAL/NONE rows remain.
- The cmux dispatch family is reachable by Claude/Codex via CLI + skill, with the Pi `/ccc:workspace:*` commands importing the same `@ji/ccc` cores, typed parity metadata covering those surfaces, and no duplicated orchestration. (Stack landing, push, autoslot, and changes already have CLI entries via `ji flow`; autobranch is fully done.) Model-text steps (slug, summary) run through the backend-neutral text-generation/model-defaults seam (`@ji/core` / `@ji/capability-kit`), not the Pi-only model harness.
- The flow-family skill/doctrine gap is resolved: each `/ji:flow:*` surface without a wrapper skill either gains one or is covered by an explicit recorded doctrine decision in the parity table rules.
- The command-output summary primitive exists as a shared CLI/helper with skill guidance and optional Pi integration only as an adapter: it writes complete stdout/stderr/combined logs to payload artifact files, returns bounded human and machine-readable summaries with profile-derived counts/excerpts where practical, treats nonzero exits/timeouts as summarized outcomes, and proves no-leak behavior with synthetic large-output tests.
- A parity-review full-sweep run (the `parity-review` route of `code-workflows`) reports no unwaived gaps and reconciles `parity-table.md` with the post-rename `@ji/*` naming (two renames of drift), captured as closure evidence.
- Evidence: targeted `just ts-check` / `just ts-test` and Python checks pass for changed areas; CLI scenario tests cover each new CLI's operations, help, and version.

## Assumptions and Risks

Assumptions:

- The generic CLI→Pi bridge and shared on-disk skills make parity a fill-the-gaps effort, not a rewrite (validated by the 2026-06-03 audit and by every closed row since: each gap was independently closable by adding a CLI entry + skill with Pi shrinking to a thin wrapper; most recently validated at scale by the Flow capability, where ten workflows became `ji flow` commands with Pi as pure CLI bridges).
- The kernel repo-local extension mechanism (`@ji/kernel` `ji` bin + capability packages exporting command groups under `.ji/extensions/`) is the durable push-down substrate: a capability that exports a `ji <group>` command table is CLI-reachable in every harness, and `registerCliCommandExtension` makes the Pi mirror free. New push-down work (cmux dispatch, summaries) should use this path, building on `@ji/clinkr` (`ts/packages/infra/clinkr/`) and `@ji/core` (`ts/packages/infra/core/`), rather than growing bespoke bins.
- Model-text neutrality is solved infrastructure: slug derivation resolves through `ts/packages/infra/core/src/primitives/model-slug.ts` (with a capability-kit split at `ts/packages/capability-kit/src/kit/model-slug.ts`), honoring `JI_SLUG_MODEL` over the shared fast-model default, and the remaining model-touching defaults are env-overridable (`PI_DRAFT_MODEL` plus the `JI_*_MODEL` family: `JI_CCC_SIDEBAR_MODEL`, `JI_CHANGES_MODEL`, `JI_CHECKPOINT_MODEL`, `JI_SUBMIT_FAILURE_MODEL`, etc.). Validated by the provider-default consolidation; new code must keep using the seam.
- The `@ji/ccc` cmux cores are extraction-ready: the dispatch orchestration is already factored into focused modules, so the remaining push-down row is CLI-entry + skill + parity-metadata work, not logic extraction (the same shape the land push-down had before `ji flow land` shipped).
- Genuinely Pi-native primitives (`dispatch_runner_subagent`, grill UI, worktree status line) are acceptable to keep Pi-only; tool-call surfaces do not require parity rows, but dependent workflows should document an agent-neutral fallback.
- The summarized-command work belongs in this umbrella because its core architectural decision is parity: command execution and log summarization must be reachable from every harness through the same CLI/helper instead of appearing first as a Pi-only convenience.

Risks:

- Parity-table rot: the table is worthless if updating it is not enforced. This risk has now materialized **seven** times: stale `/objective:gt-stacks` rows; the stale `/handoff:list` PARTIAL row; the pre-2026-06-09 backlog; the pre-2026-06-10 backlog; the post-2026-06-10 drift caught 2026-06-12; the 2026-06-26 `@asdl`→`@sdl` rename + relocation; and now the `@sdl`→`@ji` cutover plus the Flow capability landing, which changed CLI names, Pi surface names (`/code:*` flow commands became `/ji:flow:*`), skill names (`code-*` → `sdl-flow-*`), and package paths while the table's rows still carry `@asdl`-era names under a `@sdl`-era stale banner. The distributed typed parity gate now catches per-package metadata drift at test time, but the Markdown table itself keeps lagging; the standing trigger to harden table maintenance has fired three times (fifth, sixth, and seventh materializations).
- "Shared TS ≠ shared CLI": consolidating orchestration into shared packages looks like parity progress but is invisible to Claude/Codex until a CLI entry and skill exist. The cmux dispatch family is the live instance: its orchestration is cleanly factored in `@ji/ccc` yet reachable only through Pi. The `ccc` package's own bin is currently dead weight — its `package.json` bin points at `./src/sdl/cli.ts`, which no longer exists (the file is `./src/ji/cli.ts`), and no `ccc` command is on PATH — so the previously-recorded "hidden `ccc exec autobranch`" reachability path is gone; autobranch reachability now runs entirely through `ji flow autobranch`. The parity table must keep scoring reachability (CLI + skill), not code placement.
- Skill-coverage drift: the typed parity metadata self-declares all ten `/ji:flow:*` surfaces FULL with `cli: ji flow <name>`, but only four have wrapper skills, and this Objective's own FULL rule requires a skill. If the doctrine question stays unresolved, the table and the typed gate will disagree about what FULL means and new CLI-bridged commands will silently ship without any Claude/Codex-facing documentation.
- Provider lock-in drift: largely de-risked by the provider-default consolidation (hardcoded sites resolve through the model-defaults seam or per-purpose `JI_*` env overrides, and shared prompt/skill guidance carries harness-neutral defaults with labeled OpenAI/Anthropic examples per the AGENTS.md "Skill Model Examples" convention). Residual exposure is new code reintroducing hardcoded refs; the parity-review sweep's harness/model check remains the control.
- Umbrella sprawl: a cross-cutting Objective touching many subsystems can become a never-closing catch-all, and folding in the closed siblings' rows plus command-output summaries increases that risk. Mitigation: the delivered rows are tracking-only context, and summarized commands stay one bounded shared-primitive workstream with explicit completion criteria rather than a generic validation-output program.

## Open Questions

- Does FULL still require a wrapper skill now that the kernel `ji` CLI plus typed `definePiSurfaceParity` metadata exist? The flow metadata declares land/push/autoslot/changes/pull-trunk/regenerate-pr FULL without skills; this Objective's table rule says FULL needs a skill. Resolve the doctrine and record it in the parity table rules before or during the next full sweep.
- Where does the cmux dispatch CLI land: as a `ji ccc`/`ji workspace` repo-local group (matching the flow pattern), inside an existing capability group, or by repairing/retiring the broken `ccc` bin? The `ccc` bin's stale `package.json` entry (`./src/sdl/cli.ts`, missing) needs an explicit repair-or-retire decision either way.
- For the summarized-command primitive, what final command name/package should own the shared helper, how directly should it reuse the shipped payload artifact store, which concrete output formats should the first profiles parse, should Pi integration be a custom tool or command wrapper, and what hard caps should apply to transcript-visible tails/excerpts?
- The seventh parity-table-rot materialization again raises table-maintenance hardening: with per-package typed gates now shipped, should the remaining parked work (covering `@ji/ccc` and ad hoc `.pi/extensions/*.ts` adapters, and/or generating the human table from typed metadata) be promoted to active work?
- Did the former `dev-preview-url` and `objective-current` skill workflows get renamed/folded or regress across the renames? (`sdl-submit`'s workflow is re-covered by `ji flow submit` + the `sdl-flow-submit` skill.) Re-verify reachability in the next full sweep before trusting the corresponding rows.
