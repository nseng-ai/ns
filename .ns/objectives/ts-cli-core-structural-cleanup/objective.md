# TS CLI + @nseng-ai/foundation Structural Cleanup

## Thesis

A thermo-nuclear code-quality review of the TypeScript CLI fleet (15 CLIs at review time; 10 first-party `cli.ts` entrypoints at HEAD after package consolidation, capability migration, and the workspace rename) plus the shared core package found that the fleet's foundations are strong (no `as unknown as`, no broad `any`, errors-as-values throughout, gateway seams, and Zod at most boundaries) but that the same handful of concepts were reimplemented across packages instead of living once in the appropriate shared layer, and that several files/functions had crossed the size/cohesion line. This Objective tracks landing those findings as independently reviewable structural changes where they remain valid.

The full original review — with file evidence, severity, and concrete remedies for every finding — is preserved under `references/` (start at `references/README.md`). The workspace has since been renamed (`@sdl/*` → `@ji/*` → `@ns/*` → `@nseng-ai/*`, `sdlcc` → `jicc` → `nscc`, `sdl-flow` → `@nseng-ai/flow`) and rehomed, several ownership boundaries moved during the extension architecture migration, and core became a subpath-only container with its gateway substrate relocated to `@nseng-ai/capability-kit`. The reference files and older Semantic Updates therefore use retired names and paths: they are source material rather than current truth — always re-verify paths, package homes, and ownership before picking up an open row.

**Repository-layout note (rebaselined at HEAD 141ac24d).** The package scope is `@nseng-ai/*`; no live `@sdl/*`, `@ji/*`, or `@ns/*` imports remain under `ts/packages`. Current homes: `@nseng-ai/foundation` → `ts/packages/infra/foundation/` (the former `@ns/core`; container package, subpath exports only — no root `.` export), `@nseng-ai/clinkr` → `ts/packages/infra/clinkr/`, `@nseng-ai/brmem` → `ts/packages/infra/brmem/`, `@nseng-ai/kernel` → `ts/packages/kernel/`, `@nseng-ai/capability-kit` → `ts/packages/capability-kit/` (the gateway container: `graphite/`, `github/`, `git/`, `kit/brmem-cli` substrate live here), hosts `nscc` → `ts/packages/hosts/nscc/`, `@nseng-ai/pi` → `ts/packages/hosts/pi/`, and the kernel-driven `@nseng-ai/ns` umbrella → `ts/packages/hosts/ns-cli/`, tools `@nseng-ai/areg`/`@nseng-ai/packagechk`/`@nseng-ai/vibechk` → `ts/packages/tools/*`, and every capability (`pr-feedback`, `retros`, `branch-context`, `ccc`, `flow`, `handoffs`, `objectives`, `plans`, `reviews`, `slots`) → `ts/packages/capabilities/*`. `@internal/pi-tools` lives at `ts/packages/internal/pi-tools/`. The former standalone `@sdl/graphite` package is gone; neutral Graphite mechanics live in `@nseng-ai/capability-kit/graphite/*`. `@sdl/domain-primitives-transitional` has been deleted.

This Objective is the canonical home for tactical TypeScript structural cleanup and architecture-deepening findings that are *not* specifically extension-layering endgame work. It subsumes the still-live tactical rows from the closed `ts-cli-architecture-deepening` Objective. The parent `sdl-extension-architecture` Objective (ADR 0009) has since **closed** and `@sdl/domain-primitives-transitional` is deleted, so the earlier sequencing gate on that endgame is gone. After the row-by-row reclassification and the neutral slices landed through 2026-06-30, **no neutral structural-cleanup rows remain open**: every remaining open row in `roadmap.md` is capability-owned or design-sensitive and routes to its owning capability context rather than to neutral infra work here.

## Scope

In scope — the verified or still-open review findings, grouped:

- **Shared CLI wiring layer (completed):** `defineCli` in `@nseng-ai/foundation/cli-runtime` (`ts/packages/infra/foundation/src/cli-runtime/index.ts`) owns `runtimeInfo` derivation, version reading, IO/cwd/env defaulting, and the entry guard; all 10 current first-party `cli.ts` entrypoints (address, aretro, branch-context, ccc, plans, nscc, brmem, areg, packagechk, vibechk) consume it. The previously proposed `clinkr` `execGroup(description?)` factory is rejected: the existing hidden-`exec` construction was already correct everywhere, and the helper did not delete enough complexity to justify a shared abstraction.
- **Branch-Memory access unification (completed):** `branch-context` uses the in-process `@nseng-ai/brmem` `BrmemGateway`; its old `src/brmem-gateway.ts` JSON/subprocess parser is gone. The single public `runBrmem` runner (now homed at `@nseng-ai/capability-kit/kit/brmem-cli` after the substrate move out of core) preserves the two-candidate behavior (PATH `brmem`, then `pnpm exec brmem` fallback) internally; the former public candidate-iteration surface and dead `readOptionalBrmemBooleanField`/`graphqlErrorsFromJson` exports are gone. `brmem` composes the shared `GitGateway` (now `@nseng-ai/capability-kit/git`) for generic Git branch facts while keeping Branch Memory ref-encoding checks local.
- **Cross-package dedup (completed for the named items):** the original `resolveBranchOrCurrent` helper row is disposed as obsolete (no such symbol exists and no repeated policy-free helper shape remains). GitHub PR feedback leaf helpers (`ghAuthorSchema`, `normalizeAuthor`, numeric GitHub identity policy, failure-agnostic parse) are shared from `@nseng-ai/capability-kit/github/pr-feedback` and the `reviews` capability consumes them with no local divergent copies. The vestigial core root `.` export is deleted: `@nseng-ai/foundation` exposes only curated subpaths, and the former bare importer (`ts/packages/hosts/pi/src/kit/sessions/harness-session.ts`) imports from `@nseng-ai/foundation/primitives`.
- **God-file / god-function decomposition (completed):** `@nseng-ai/areg`'s `ts/packages/tools/areg/src/real-gateways.ts` is a 6-line compatibility export surface with the project gateway, filesystem/path-safety, mutation-policy descriptor data, and skill-kind classification split under `src/gateways/`. The Flow land-stack god-file is resolved by Flow-owned restructuring: `ts/packages/capabilities/flow/src/land/stack/landing-operations.ts` is 308 lines, `performGraphiteMaintenance` lives in a dedicated `graphite-maintenance.ts`, and the land-stack directory is split into ~20 focused modules (landing-plan, landing-plan-execution, landing-coordination, presentation, pre-merge-*, worktrees, backup-refs, …). `@nseng-ai/ccc` no longer carries a land-stack re-export file; `ts/packages/capabilities/ccc/src/ns/land.ts` re-exports from `@nseng-ai/flow/api`.
- **Graphite boundary convergence (open, rebaselined):** neutral Graphite mechanics (branch, metadata, stack, status, testing fakes) now live in `@nseng-ai/capability-kit/graphite/*`; Flow retains land-specific topology reads (`land/stack/graphite-topology.ts`, `stack-facts.ts`, `graphite-command-channel.ts`) as Flow policy. Remaining work, if any, is extracting only policy-free mechanics into `@nseng-ai/capability-kit/graphite` when a pickup proves real duplication; landing-path decisions and `/ns:flow:land` behavior stay Flow-owned.
- **Boundary / Zod / type-contract cleanups (completed except capability-owned remainders):** `nscc`'s `stack-map-model-loader.ts` (Zod boundary schemas, `json-fields.ts` deleted), `@nseng-ai/kernel`'s extension discovery (now `src/extensions/discovery.ts`, Zod manifest schemas, `MANIFEST_COMMAND_FIELDS` gone), `@nseng-ai/packagechk`'s claim runners, and `@nseng-ai/vibechk`'s workflow cleanup are all landed. Remaining candidates are capability-owned: `@nseng-ai/retros`'s `sessions/pi-jsonl-source.ts` and Flow-owned submit/PR-description code under `ts/packages/capabilities/flow/src/submit/`.
- **Small dedup / absorbed architecture-deepening rows (reclassified):** ccc/flow small helper dedup (e.g. `firstNonEmptyLine`, `isRecord` copies) and ccc cmux/slot dispatch are capability-boundary work; slot inventory reconciliation, slot Graphite navigation, and Branch Memory entry-locator rows are disposed/absorbed by current Slot and brmem designs; objective-markdown validation (`ts/packages/capabilities/objectives/src/core/operations/check-objective.ts`) and branch-context plan-attachment seams (`ts/packages/capabilities/branch-context/src/core/attach.ts`, `attached-plan.ts`) belong to Objective and Branch Context/Plans respectively.

## Non-Goals

- No behavior changes. Every item must preserve observable CLI behavior; this is a structural/quality Objective, not a feature or bugfix Objective.
- Not a VCS/commit/stack-packaging review — out of scope by construction.
- Do not collapse genuinely distinct gateway *interfaces* (for example the `reviews` capability's REST PR-files surface vs the shared GraphQL feedback gateway, or areg's domain-scoped project gateway). Only shared *leaf helpers*, mechanics, and policy are candidates for unification.
- Do not force `objective` filesystem records onto the Branch-Memory ref gateway; its storage model is legitimately different.
- Do not parallelize intentionally sequential flows such as land-stack merge/ref cleanup or gh rate-limited submit loops; those orderings are correctness constraints.
- Do not touch vendored third-party code under `.agents/skills/`.
- **ADR 0009 layering guardrail (restated with current names).** Do not move duplicated capability-domain logic into below-SDK neutral packages merely because it is duplicated. Before pulling shared code "down," classify it against ADR 0009 layering: neutral infra lives below the SDK (`@nseng-ai/foundation`, `@nseng-ai/clinkr`, `@nseng-ai/brmem`), the above-SDK shared substrate is `@nseng-ai/capability-kit` (which now also owns the neutral Graphite/GitHub/Git gateway mechanics), and capability domain lives in its capability package / Capability API. `@sdl/domain-primitives-transitional` has been deleted; nothing routes there anymore. Deduping a leaf helper or policy is in scope; relocating capability-domain logic below the SDK to remove duplication is not.

## Completion Criteria

- The shared `defineCli` helper exists and all current CLIs consume it; `runtimeInfo`/version/entry-footer boilerplate is gone from individual `cli.ts` files. **Met** at `@nseng-ai/foundation/cli-runtime`. The `execGroup(description?)` helper is explicitly not a completion requirement after review rejected it as an underpowered shared abstraction.
- `branch-context` reads/writes Branch Memory through the in-process gateway; the parsing half of its old `brmem-gateway.ts` and its former core `brmem-cli` dependency are deleted; the brmem-cli candidate framework is collapsed behind `runBrmem` while preserving fallback behavior. **Met** (with `runBrmem` since rehomed to `@nseng-ai/capability-kit/kit/brmem-cli`).
- The remaining named cross-package duplications are either unified to a single canonical implementation, explicitly reclassified as no-longer-valid, or routed to their owning capability context in `roadmap.md`. **Met for the named items** (GitHub leaf helpers unified in capability-kit; `resolveBranchOrCurrent` disposed); the still-open small-dedup rows carry explicit capability-owned routing.
- `@nseng-ai/areg`'s `real-gateways.ts`, Flow/ccc land-stack maintenance logic, and any still-live god-files/functions are decomposed below the cohesion line with message/presentation separated from mutation/business logic where applicable. **Met**: areg decomposed here; the Flow land-stack decomposition landed as Flow-owned work.
- The per-package boundary/Zod/type cleanups are either landed in their current package homes or intentionally routed to the owning capability context. **Met except** the capability-owned `retros` (aretro) and Flow-submit rows, which remain open with routing recorded in `roadmap.md`.
- Evidence: the relevant TypeScript gates pass for each landed slice, and behavior parity is confirmed by existing or focused CLI scenario tests for affected commands.

## Assumptions and Risks

Assumptions:

- The original review findings are useful source material but not current truth. The `@sdl/*` → `@nseng-ai/*` scope renames, the `sdlcc` → `nscc` rename, the core-to-container conversion, and the capability-kit gateway consolidation mean every path/name in `references/` and in pre-rename Semantic Updates must be re-mapped before use.
- The CLI scenario tests plus the normal TypeScript gates are a sufficient behavior-parity net for refactors of this shape when paired with focused tests around the moved seam.
- The original `execGroup(description?)` recommendation over-weighted repeated syntax and under-weighted abstraction cost. Future shared-helper rows should clear a stronger bar: delete meaningful complexity, prevent plausible drift, or encode a non-obvious invariant.
- The remaining open rows are correctly classified capability-owned/design-sensitive; none is a neutral cleanup this Objective should implement directly. If a future pickup disproves a classification, reclassify the row before implementing.

Risks:

- Land-stack Graphite maintenance still mutates local Graphite refs after irreversible merges. The decomposition landed (`graphite-maintenance.ts` is a dedicated Flow module), which reduces but does not remove the risk: any future change must preserve the expected-SHA snapshot and merge→verify→cleanup ordering exactly.
- Branch-Memory access has a compatibility hazard around ref encoding and fallback behavior. The landed `runBrmem` simplification deliberately preserved the PATH→`pnpm exec brmem` fallback; future entry-locator or plan-attachment work must be compatible/append-only and covered with its own tests before migrating callers.
- A shared CLI entrypoint helper touches every CLI at once; future changes to `defineCli` must keep scenario coverage for `--version`, `--runtime`, and help/entry behavior.
