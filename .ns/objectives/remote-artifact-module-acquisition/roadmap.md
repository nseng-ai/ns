# Roadmap

## Work

Design decisions (steer-first; record each as a Semantic Update before implementing):

- [x] Decide the source-spec grammar and first-slice source kinds.
      **Decided 2026-07-07** (see `updates/20260707T182049Z-source-spec-grammar-decision.md`): adopt pi's grammar shape verbatim as the durable grammar (`npm:pkg[@ver]` / `git:host/user/repo@ref` / local path); slice one ships **npm-only**, with git and local-path reserved until the storage and gateway decisions land. Pinning semantics adopted with the grammar: versioned npm specs pinned/skipped, unversioned reconciled, git refs reconciled-not-advanced. Malformed/unknown specs are per-entry diagnostics. The local-path acquisition-vs-pointer question stays open.
- [x] Decide the fetched-module storage location and its explicit, inspectable record, plus how discovery reads it.
      **Decided 2026-07-07** (see `updates/20260707T184938Z-managed-extensions-storage-and-model-decision.md`; refined by `updates/20260707T190752Z-pi-aligned-fetch-mechanics-and-dependency-behavior.md`): consumption-agnostic acquisition owned by a new acquisition-only subpackage (working name `@nseng-ai/extensions`); ns.toml key **`extensions = [...]`** (supersedes the `artifact-packages` working name); managed root **`.ns/managed-extensions/`** (gitignored via repo-root `.gitignore`, written by `ns init` in consumers), with pi-aligned source-kind subdirs. Npm uses one private managed package project per canonical identity at `.ns/managed-extensions/npm/<pkg-name>/`, with the installed top-level module at that leaf's `node_modules/<pkg-name>` (superseded 2026-07-10 by `updates/20260710T145816Z-per-package-npm-project-isolation.md`; legacy shared-project bytes are ignored); git clones remain under `git/<host>/<path>`. **No lockfile** — the spec is the record, resolved state inspectable via fetched `package.json` + manifest provenance; discovery gains the managed root as a third root reusing the existing walk. Slice one wires only artifact discovery; kernel command loading from fetched content is deferred to the trust re-judgment row.
- [x] Decide fetch mechanics and the acquisition gateway seam (registry access, git transport, fake-driven tests; no real network in tests).
      **Decided 2026-07-07** (see `updates/20260707T190752Z-pi-aligned-fetch-mechanics-and-dependency-behavior.md`): follow pi's package-manager acquisition model rather than npm tarball extraction. Slice-one npm acquisition creates a private managed npm project, installs declared specs with peer/host dependency suppression, permits normal runtime dependencies, and reports per-extension acquisition diagnostics. Git behavior is reserved but follows pi's direct clone layout with dependency install inside the clone. The acquisition package exposes gateway seams for package-manager/npm commands and git commands; tests use fakes and never perform real network fetches.
- [x] Decide how acquisition composes with `ns update` (inside unconditionally, flagged, or a separate composed verb) and the per-source update/pinning semantics command contract (pinned skipped; unpinned reconciled to spec).
      **Direction set 2026-07-07** (`updates/20260707T193019Z-...`); **contract decided 2026-07-07** (see `updates/20260707T200657Z-ns-update-acquisition-command-contract-decision.md`): pi-verbatim modes — bare `ns update`/`--self` = self-update only, `--extensions` = acquire + reconcile/provision, `--all` = both, per-spec targeting of declared specs. **Superseded on trunk** (see `updates/20260712T171229Z-extension-lifecycle-supersedes-pi-verbatim-update-contract.md`): the `ns extension` lifecycle group (`install`/`update <source>`/`uninstall`, owned by `ship-objectives-to-customers`) replaced the pi-verbatim `ns update` modes; bare `ns update` is a reserved self-update surface and `--extensions` is a rejected retired flag. The per-source pinning semantics survive as `refresh-floating` / `ensure-pinned` / `local-in-place` acquisition intents; removal graduated from report-only diagnostics to a real identity-matched `ns extension uninstall` verb.
- [x] Re-judge the carried trust-posture risk acceptance with real fetch semantics on the table; record the outcome (continue accepting under the trusted-repo contract, or escalate to the umbrella). **Now also owns:** whether the kernel may load command extensions (executable code) from fetched managed-root modules — per-consumer wiring deferral in the storage decision (`updates/20260707T184938Z-...`).
      **Decided 2026-07-07** (see `updates/20260707T193019Z-trust-deferral-executable-extensions-and-update-composition-direction.md`): trust gate deferred — risk acceptance continues under the explicit trusted-repo assumption, no consent gate in this record; pi's trust-store/`--approve` model is the blueprint for a fresh Objective if ns's audience widens. Kernel loading of executable command/CLI-group extensions from fetched managed-root modules is **allowed** as a later slice (after passive artifact wiring, once the kernel extension contract is explicit).

Implementation (after the decisions above):

- [x] `ns.toml` declaration list (`extensions = [...]`, per the storage decision): schema, parsing, and diagnostics in the ns-toml layer.
      **Implemented 2026-07-07** (see `updates/20260707T210000Z-local-filesystem-pointer-dogfood-sequencing.md`): top-level local extension declarations parse with diagnostics; table-local entries are ignored. Since extended on trunk: `ts/packages/kernel/src/project-config/ns-toml-extension-syntax.ts` scans the top-level `extensions` assignment on a shared TOML statement scanner, and `ns-toml-extensions-edit.ts` edits the array format-preservingly for the install/uninstall lifecycle.
- [x] Acquisition slice one: fetch + resolve declared specs of the first-slice source kind(s) into the decided storage root behind the gateway, with per-module failure diagnostics that do not block provisioning of present modules.
      **Implemented 2026-07-07** (see `updates/20260707T211500Z-npm-managed-acquisition-declared-extensions.md`): declared npm specs resolve through the kernel acquisition API into per-identity private projects at `.ns/managed-extensions/npm/<pkg-name>/node_modules/<pkg-name>` behind fakeable gateways (layout superseded 2026-07-10 by `updates/20260710T145816Z-per-package-npm-project-isolation.md`); pinned specs skip when present, unpinned specs install on apply-mode update, and acquisition failures surface as per-extension diagnostics.
- [x] Wire acquired modules into existing discovery and the update/reconcile flow; prove idempotence on unchanged specs and reconcile-to-spec on changed specs.
      **Implemented 2026-07-07** (see `updates/20260707T211500Z-npm-managed-acquisition-declared-extensions.md`) against the then-current static-declaration discovery and `ns update --extensions`. At HEAD the wiring shape is: declared specs resolve to package roots (managed npm or local in-place), descriptors load from those roots (`ts/packages/kernel/src/project-config/points.ts`, `declared-descriptors.ts`), and `discoverDeclaredExtensionModuleHarnessArtifacts` feeds the manifest-aware activation reconciliation run by the `ns extension` lifecycle verbs; exact-spec installs are idempotent and updates reconcile to spec.
- [x] Wire the `ns update` command surface for acquisition.
      **Implemented 2026-07-07** as the pi-verbatim modes (bare/`--self`/`--all` failing with `self-update-not-implemented`, `--extensions` owning the reconcile path, declared-only local targeting). **Superseded on trunk** by the `ns extension` group (see the composition decision row above and `updates/20260712T171229Z-...`): `ns extension install` acquires + records the exact spec + runs full activation reconciliation; `ns extension update <source>` is single-target with explicit acquisition intents and `--dry-run`; `ns extension uninstall` is identity-matched with managed-project removal and scope pruning. `hosts/ns` CLI tests assert `ns update --help` no longer advertises `--extensions`/`--all`/`--force` and that `ns update --extensions` is a usage error.
- [ ] End-to-end evidence: one real remote module declared (`ns extension install npm:...`), fetched from the registry, and provisioned into `pi`/`claude-code`/`codex` roots with manifest hashes; preinstalled and local arrival paths verified unchanged; full `just` green.
      Note: current acquisition/adapter tests use fake exec channels only — no real-registry fetch has been evidenced. `ship-objectives-to-customers`' bare-core unbundle + checkout-free verification rows (`ns extension install npm:@nseng-ai/objectives` in a foreign repo) would satisfy this row; if that thread stalls, produce equivalent evidence here.
- [ ] Build the ns self-update mechanism behind the reserved bare `ns update` surface (added 2026-07-07 by user instruction with the composition decision; sequenced after the acquisition slices). Until it lands, bare `ns update` fails with `self-update-not-implemented` pointing at `ns extension update <source>` (`ts/packages/capabilities/harness-artifacts/src/ns/update.ts`).
