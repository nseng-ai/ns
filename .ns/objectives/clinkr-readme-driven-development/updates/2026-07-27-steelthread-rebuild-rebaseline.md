# Steelthread Evidence Rebaselines Clinkr Toward a Clean Rebuild

## Summary

The implementation stack from `clinkr-immutable-app-builder-runtime` through `colocate-objectives-cli-remove-operations` successfully proved the filesystem-oriented Clinkr authoring result across Clinkr, Foundation, the SDK host, Flow, Objectives, and Brmem. It also demonstrated that the implementation reached that result through parallel transitional mechanisms: immutable nodes lowered into the legacy mutable runtime, SDK pre-selection preceded real dispatch, filesystem topology was traversed repeatedly, validation and rendering retained compatibility owners, and descriptor typing remained permissive.

The user chose to treat that stack as an executable steelthread rather than production architecture to polish. The Objective now returns to its contract base with the steelthread's contract refinements incorporated into the blessed `references/README-draft.md`. `references/steelthread-contract-changes.md` records the public-contract changes and reopened questions. `references/steelthread-implementation-lessons.md` records the implementation failures, root causes, successful evidence, rebuild rules, and test doctrine.

Historical Semantic Updates remain unchanged. Their decisions and validation evidence are preserved; this update changes how the prototype implementation is used going forward.

## Objective Impact

The Objective's implementation phase is rebaselined from “finish the in-place clean cut” to “perform a clean rebuild from the blessed README and steelthread evidence.” The filesystem result, strict two-file command seam, Clinkr-owned `src/cli/` topology, complete usage-error schema composition, presentation-ready string rendering rule, and status-specific outcome validation are retained. Prototype compatibility interfaces and branch ancestry are not presumed reusable.

Completion now requires one runtime, one routing traversal, one validation/rendering owner, truthful context-free typing, a decoded SDK descriptor union, recursively lazy topology, explicit completion ownership, and removal of all migration seams before broad caller migration. Tests and consumer scenarios may be ported selectively, but tests that preserve transitional architecture are not completion evidence.

## Follow-Ups

- Review and bless the refreshed README examples and the reopened lower-interface questions before TypeScript implementation.
- Rebuild in a narrow sequence: README fixtures, Clinkr runtime/topology, one standalone consumer, SDK composition, Objectives real-host acceptance, then remaining callers.
- Return the steelthread's process lesson to `foundation-readme-driven-pass`: when a README-driven steelthread proves the product interface but reveals central parallel machinery, preserve evidence and rebaseline before broad migration rather than converting compatibility scaffolding into the final architecture.
