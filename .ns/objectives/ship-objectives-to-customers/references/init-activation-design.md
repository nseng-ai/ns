# `ns init` and extension activation (design draft)

> Status: README-driven design draft for the descriptor activation surface (roadmap row:
> "Design the descriptor activation surface for generic `ns init`"). Companion to
> `README-draft.md` (the `ns extension` acquisition surface). The main body is written as
> the future customer-facing doc, as if shipped. Design notes, positions taken, and the
> migration plan are at the end. Settled inputs from the 2026-07-09 activation-surface
> design session with the owner: trunk detection is generic git posture; `AGENTS.md` gets
> a minimal pointer stanza; instruction content lives in a committed, tool-owned
> `.ns/instructions.md`; extensions contribute activation content as plain data on the
> descriptor; the orientations instruction ships in the objectives extension's section.

`ns init` activates ns in a repository. It is a core built-in — it must work on a bare
`@nseng-ai/ns` install with no extensions — and every duty it performs is
extension-agnostic. Extension-specific activation content (agent instructions, consumer
directories) comes from the installed extensions' descriptors; `init` only orchestrates.

## What `ns init` does

1. **Verifies git posture.** The working directory must be inside a git repository with a
   detectable trunk branch — ns is git-native and anchors durable state to the repo.
   Verify-and-write only: `init` never stages or commits.
2. **Selects and persists harnesses.** Explicit repeatable `--harness` (one of
   `claude-code`, `codex`, `pi`) on first run, persisted to top-level `harnesses = [...]`
   in `ns.toml`; later runs may omit the flag and reuse the persisted selection.
3. **Wires agent instructions.** Writes one small managed stanza into `AGENTS.md`
   pointing at `.ns/instructions.md` (plus the `CLAUDE.md → @AGENTS.md` import), and
   regenerates `.ns/instructions.md` from the installed extensions (below).
4. **Scaffolds `.ns/`.** Ensures the `.ns/` directory, the `.ns/managed-extensions/`
   gitignore rule, and each installed extension's declared consumer directories.
5. **Provisions harness artifacts.** Installs every installed extension's
   `bundledArtifacts` (skills) into the selected harnesses' roots.
6. **Reports.** A structured per-duty change report (`created` / `replaced` /
   `unchanged` / …) in both human and `--format json` output.

Re-running `ns init` is always safe and idempotent: an already-activated repository
reports `unchanged` everywhere. Run it again after installing or removing extensions to
reconcile — though the `ns extension` commands also reconcile on their own (below), so
either order works.

## The two instruction files

### `AGENTS.md`: one minimal, permanent stanza

`ns init` writes exactly this into the repository's `AGENTS.md` (created if absent):

```markdown
<!-- ns:begin v1 -->

Read @.ns/instructions.md before working in this repository — ns tooling
instructions for agents (generated file).

<!-- ns:end -->
```

That is the entire ns footprint in the customer's file. It is written once and then
essentially never touched again: installing, removing, or upgrading extensions never
rewrites `AGENTS.md`. The fence markers let `init` find and verify (or version-bump) the
stanza on re-runs; everything outside the fence is the customer's and is never modified.

The line does double duty across harnesses: Claude Code chain-loads the referenced file
through its import mechanism (`CLAUDE.md → @AGENTS.md → @.ns/instructions.md`), while
Codex and Pi read it as an imperative instruction and open the file themselves.

### `.ns/instructions.md`: committed, tool-owned, fully generated

All real instruction content lives in `.ns/instructions.md` — a **committed** file that
ns owns completely. No fences, no merging with user content: ns regenerates it wholesale,
top to bottom, whenever `ns init`, `ns extension install`, `ns extension uninstall`, or
`ns extension update` runs.

```markdown
<!-- Generated by ns. Do not edit; regenerated by `ns init` and `ns extension` commands. -->

# ns instructions

This repository uses ns. `ns.toml` declares its harnesses and extensions; run
`ns --help` for the available command surface.

## Objectives

This repository uses ns Objectives: durable planning records under `.ns/objectives/`
that carry work across sessions and branches.

- Before starting non-trivial work, run `ns objective list` and read any Objective that
  overlaps your task (start with its `objective.md` and `roadmap.md`).
- Also run `ns objective exec load-orientations --format md` and treat any output as
  standing repository rules while present.
- Use the `ns objective` CLI and the objective skills to create, advance, update, and
  close Objectives.
```

The structure is: a generated-file header, a short core preamble, then one section per
installed extension that declares instructions, in `ns.toml` `extensions = [...]`
declaration order (deterministic, and reorderable by editing `ns.toml`). A bare-core
repository gets the header and preamble only.

Because the file is committed, teammates' agents get the instructions on a fresh clone
before anyone runs ns, and instruction changes show up in review like any other change.

## The descriptor `activation` field

Extensions contribute activation content through one optional field on the extension
descriptor (see "Writing an ns extension"), alongside `entries`, `points`, and
`bundledArtifacts`:

```ts
export default defineExtension({
	group: "objective",
	description: "Inspect and maintain ns Objective records.",
	entries: [/* … */],
	activation: {
		instructions: OBJECTIVES_INSTRUCTIONS, // markdown section, starts with a `## ` heading
		consumerDirs: [".ns/objectives"], // created with .gitkeep; never deleted by ns
	},
	bundledArtifacts: [/* skills, provisioned per harness */],
});
```

- **`instructions`** (optional string): one markdown section, starting with a `##`
  heading, appended verbatim into `.ns/instructions.md`. Anything the extension wants
  agents told — including instructions to run its own commands, like objectives'
  `load-orientations` line — lives here, owned and versioned by the extension package.
- **`consumerDirs`** (optional string array): repo-relative directories under `.ns/` that
  the extension's durable consumer data lives in. `init`/`install` create them (with
  `.gitkeep`); `uninstall` **never** deletes them — consumer data outlives the extension.

The field is plain data, Zod-validated with the rest of the descriptor, and keeps the
descriptor's cheap-to-execute contract. There is deliberately **no activation hook**: ns
core does all file writing, so it can guarantee idempotent re-runs, surgical uninstalls,
and that nothing outside ns-owned files is ever touched. (Rejected alternative recorded
in the design notes below.)

## Lifecycle semantics

| Event                    | Effect on activation state                                                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ns init`                | Full pass: posture, harnesses, `AGENTS.md` stanza + `CLAUDE.md` import, `.ns/` scaffolding + ignore rules, regenerate `.ns/instructions.md`, create all `consumerDirs`, provision all `bundledArtifacts`. |
| `ns extension install`   | After acquisition + `ns.toml` recording: regenerate `.ns/instructions.md`, create the extension's `consumerDirs`, provision its artifacts (or hint `ns init` if no harness is configured yet).            |
| `ns extension uninstall` | Regenerate `.ns/instructions.md` without the extension's section; deprovision its manifest-tracked artifacts; leave `consumerDirs` and their contents untouched. `AGENTS.md` untouched.                   |
| `ns extension update`    | Re-acquire, then regenerate `.ns/instructions.md` and re-reconcile artifacts (the new version may ship different instructions).                                                                           |

Regeneration is wholesale and derived only from `ns.toml` plus installed descriptors —
there is no incremental section patching and no state beyond the declared extension list.

## Design notes and decisions (not part of the shipped doc)

Decisions from the 2026-07-09 activation-surface design session (owner-confirmed):

1. **Trunk detection is generic git posture**, kept in core `init`. The current
   objectives-specific failure wording ("objectives need one to anchor durable records",
   `activate-objectives.ts`) is reworded to be ns-generic.
2. **Pointer-stanza architecture.** `AGENTS.md` carries only the minimal fenced pointer;
   all content lives in tool-owned `.ns/instructions.md`. This dissolves the
   per-extension fence-composition problem entirely (no shared-fence vs per-extension
   fence choice, no surgical section removal in a user-owned file), makes uninstall
   trivially safe, and turns instruction upgrades into tooling releases instead of
   managed-block version bumps in every customer's `AGENTS.md`.
3. **`.ns/instructions.md` is committed** (owner call): git-native durable state,
   team-shareable on clone before ns is installed, low churn (regenerates only on
   init/install/uninstall/update). The name deliberately avoids `.ns/AGENTS.md` —
   harnesses attach directory semantics to that filename, and this file is ns's.
4. **Plain-data contributions, no activation hook.** Nothing objectives needs requires
   code: its activation is one markdown section and one directory. Data keeps init's file
   mutations bounded and auditable (the descriptor says *what*, core alone decides *how
   and where*) and preserves core's idempotence/uninstall guarantees. Revisit only if a
   future extension proves data cannot express its need.
5. **Orientations ship day-one, in the objectives section.** The
   `load-orientations` instruction line is owned by the objectives extension's
   `activation.instructions` (the command belongs to that extension; a bare-core repo has
   no such command). This supersedes the 2026-07-01 lean-block exclusion of
   `load-orientations`: that exclusion priced upgrades against customer-owned
   `AGENTS.md` edits, and the pointer architecture removes that cost. The output is
   computed live at agent runtime, so it is never stale; a repo with no orienting
   objectives gets empty output, harmlessly.
6. **No migration machinery.** The fat `ns:objectives:*` block exists in no real
   repository — this repo's own `AGENTS.md` is hand-authored and was never generated by
   `ns init`; the old fence appears only in `ns-init` source and tests. Migration is
   therefore an in-place code-and-test change in this repo as part of the implementation
   slice, not a runtime migration path.

Per-harness loading caveat (verification item for `cross-harness-parity`): only Claude
Code ambiently chain-loads `.ns/instructions.md` via imports; Codex and Pi depend on the
agent obeying the pointer's imperative line (one file read per session). This is a modest
reliability step down from content-in-`AGENTS.md` on those harnesses, accepted for the
Claude-Code-first slice; the Codex/Pi end-to-end verification rows should confirm agents
reliably follow the pointer.

Contract-shape coordination: `activation` is a new optional field on the promoted
descriptor contract (`ts/packages/kernel/docs/writing-an-ns-extension.md`), added under
`extension-descriptor-contract`'s policy on public-shape changes at implementation time.
It follows the existing field conventions (optional, declarative, Zod-validated, cheap).

Implementation shape (the de-objectives-ify slice):

- `instruction-block.ts`'s objectives content and the `.ns/objectives/` creation move out
  of `@nseng-ai/ns-init` into `@nseng-ai/objectives`' descriptor `activation` field.
- `activateObjectives` generalizes to an extension-agnostic activation operation that
  loops over installed descriptors; the `SkillMaterializer` seam generalizes from
  "materialize objective skills" to "provision all installed extensions' artifacts"
  (driving the existing `ns skills` machinery).
- `@nseng-ai/ns-init` keeps its name and private/folded packaging — it is the ns product
  bootstrapping itself, now with zero knowledge of any specific extension.

Parked (recorded, not designed): conditional per-harness instruction sections;
extension-contributed content beyond markdown + consumer dirs (for example `[points]`
config templates); a user-scope instructions layer.
