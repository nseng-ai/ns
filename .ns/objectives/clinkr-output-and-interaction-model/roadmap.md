- [x] Replace general whole-stream input on the bounded modern path with the smallest finite JSON-specific contract. Prefer a supplied JSON text value over a reader callback unless the inventory proves lazy acquisition is needed. Keep JSON parsing, schema validation, source-conflict checks, and command-specific errors with Clinkr or the owning command. Evidence: PR #4166 first migrated Clinkr, Foundation, SDK, Extension Kit, PR Feedback, and Reviews to finite JSON input; its follow-up correction makes Clinkr the public owner of reusable inline/file/host source selection plus JSON parsing/schema validation, renames the lazy host capability to `readJsonInput`, and removes the Extension Kit helper surface.
- [x] Keep interaction semantic and host-owned. Preserve only demonstrated confirmation and selection operations; use strict fakes in tests, `ctx.ui` in Pi, and an optional standalone rich-library adapter or documented adapter proof. Do not expose terminal streams, line readers, raw mode, key events, cursor state, or resize behavior through shared command types. Evidence: runner checkpoint `710a8f06b03cced1d40b3da207228610ac6d163f` makes every ns host provide confirmation and selection with named results, makes Pi delegate only to `ctx.ui`, and reports an explicit error when the requested UI operation is unavailable; parent-focused verification passed 49 host tests. Clinkr is now the canonical owner of `ConfirmationResult` (including `cancelled`) and `SelectionResult<T>`; the SDK reuses those result types, and a missing host capability remains an error.
- [x] Make structured output and rendering capability explicit per invocation. Preserve standalone process-backed adapters, provide capture sinks and non-ANSI capability for tests and Pi, sanitize terminal controls at the Pi presentation seam, and avoid introducing a mandatory semantic Response/event protocol. Decide separately whether Pi rejects raw commands or supports their existing byte sinks based on the actual exposed-command inventory. Evidence: the modern Foundation adapter now resolves capabilities from each invocation's actual sink and passes one coherent value into SDK contexts; Pi explicitly requests settled non-TTY plain output and normalizes complete captured transcripts before storage or presentation; focused Foundation, real-Flow SDK, Pi Runtime, and Flow Pi adapter tests cover standalone/hosted capability selection, structured progress, raw-byte capture routing, split terminal escapes, controls, completion hooks, and presentation fallbacks. Current Flow Pi lifecycle commands are structured; generic decoded raw output remains capture-and-sanitize text without PTY or terminal virtualization support.
- [ ] Qualify the reduced surface end to end. Cover standalone finite JSON request input; fake-driven request, output, and interaction behavior; Pi success and failure presentation; Pi confirmation or selection; explicit no-UI behavior; no ambient process stdin/stdout/stderr during embedded structured execution; non-ANSI rendering; control-sequence sanitization; and relevant lifecycle behavior such as idle waiting and stale-context avoidance.
- [ ] Synchronize only the durable documentation warranted by shipped ground truth. Update the relevant Clinkr, Foundation, SDK, Pi, and workflow docs to describe finite JSON request input, semantic interaction, invocation-scoped output, and host ownership; remove stale portable Saved Plan guidance. Add or update CONTEXT.md only after implementation establishes vocabulary.
- [ ] Write a final follow-up document on future directions. Record semantic Response/event modeling, richer terminal adapters, streamed progress/notices, raw-command or PTY virtualization, and additional hosts such as MCP. For each direction, name the concrete evidence that would justify reopening it and state that it is not part of the current supported surface or this Objective's completion gate.

## Parked

- A unified Request/Response/Progress/Notice/Elicitation ontology.
- `ClinkrResponse`, `ClinkrFinalPresentation`, or a general event stream absent a concrete consumer that cannot use invocation-scoped output capture.
- Arbitrary rich terminal libraries inside Pi; use Pi runtime extension UI capabilities instead.
- PTY, raw-mode, key-event, full-screen, cursor, resize, and terminal-session virtualization.
- Third-host generalization, including MCP, until a concrete production consumer exists.
- Comparative framework research unless a specific implementation decision cannot be made from current consumers and adapters.
- Repository-wide migration or deletion of unrelated legacy Clinkr APIs.
