# Slots Consumer Accounting Reconciled

## Summary

The current checkout's Slots consumers and exact package-identity references are now durably classified. The canonical presence fact for ns commands is the effective ns command catalog's exact, case-sensitive package-name set: `ExtensionCommandEntry.requiresExtension` filters commands before candidate loading and `NsExtensionApi.hasExtension(packageName)` reads the same set. The SDK owns this mechanism, and the ns host composes the real API; neither package depends on Slots. Source-workspace discovery, explicit preinstalled metadata, and valid project declarations contribute catalog identities, but those identities are configuration/catalog facts rather than consumer dependency edges.

## Objective Impact

The durable consumer-accounting roadmap row is complete. Every audited relationship now has a classification, the appropriate presence or identity signal, absent-capability behavior, and either implementation evidence or a named owner.

The audit also reconciles stale language in `flow-slots-opt-in`: its records still describe a future `kernel` registry seam and mark that seam open, but the implementation now lives in `@nseng-ai/sdk` and the ns host. `requiresExtension` and `hasExtension` are implemented, documented, and tested against one effective package-name set. Flow has not consumed those surfaces yet, so its remaining semantic work is the Flow-owned autoslot decoupling, land degradation, manifest cleanup, tests, and README contract—not construction of a new presence mechanism.

This accounting does not mark the linked Flow row complete and does not weaken any current hard workflow prerequisite. The final synthesis row remains gated on Flow delivery or explicit re-delegation.
