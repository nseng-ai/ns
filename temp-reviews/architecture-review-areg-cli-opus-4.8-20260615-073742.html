Architecture review — areg CLI

packages/areg · 2026-06-15

Five deepening opportunities. The theme: areg knows a lot about the on-disk shape of an installed skill — skills/<name>/, its mirror symlinks, its sidecar, its Pi exclusion — but that knowledge is re-derived inline across checks and commands instead of sitting behind one deep interface.

Callers ask layout.skill_md, layout.agents_symlink, layout.expected_agents_target. The seam is the layout, not raw Path arithmetic.

Problem

The canonical on-disk layout of an installed skill is re-derived inline everywhere; no module owns it.

Solution

A SkillLayout(project_dir, name) value object exposing every canonical path and expected symlink target.

Wins

  • locality: symlink targets defined once
  • leverage: one interface, six call sites
  • deletion test: complexity reappears across 6 checks
  • interface is the test surface for layout facts

Two independent hand-rolled scanners for the same delimited block. The read path and the flag-write path share no representation.

After — one deep frontmatter module

parse · read flag · set/clear flag

frontmatter module

Edit operations sit beside the parser. disable-model-invocation becomes one operation, not two parsers that must agree.

Problem

command.py re-implements frontmatter boundary scanning to flip a flag the read parser already understands.

Solution

Move flag set/clear next to the parser; both read and edit cross one seam over the SKILL.md frontmatter.

Wins

  • locality: one scanner, one set of edge cases
  • read and write can't drift apart
  • flag logic testable without the CLI
  • interface shrinks; ~55 lines absorbed
Worth exploring in-process #3

One edit-plan, one apply seam

init_project.pycommand.pyfile_plan.py

Before — two plan types, two apply loops

init_project.py

InitPlan(text_files) · own apply loop

command.py

CommandEditPlan(text/delete/dirs) · own apply + dry-run echo

file_plan.py

atoms only: apply_text / apply_delete / apply_remove_dir

Each command owns its aggregate and its loop; dry-run echo lives in command.py only.

After — one aggregate, one apply

EditPlan

text + delete + remove-dir

apply(plan, *, project_dir, dry_run) → echo

init_project.py · command.py

build EditPlan, hand it to apply()

Dry-run reporting and ordering live once. Both commands cross the same seam.

Problem

InitPlan and CommandEditPlan duplicate the "collect edits, apply them" shape with divergent dry-run behavior.

Solution

One EditPlan aggregate over file_plan atoms, with a single apply that owns echo + ordering.

Wins

  • locality: dry-run echo in one place
  • leverage: every command reuses one apply
  • init gains dry-run for free
  • one apply surface to test

One deep read of converted-skill state; callers only classify it into issues or status labels.

Problem

The invoke-only check re-derives flag/sidecar/exclusion/replacement state that command_conversion already reads.

Solution

Have the check consume CommandConversionState; keep only the state→issue mapping in the check.

Wins

  • locality: one definition of "converted"
  • check and list agree by construction
  • state read tested independent of issues
  • delete one hand-built state assembly
Speculative in-process #5

Hand checks facts, not a raw data bag

check/context.pycheck/models.pycheck/checks/*
The SkillCheck / ProjectCheck seam itself is justified — seven adapters cross it. This candidate touches only the context the seam carries, and pairs with #1.

Before — wide bag, each check uses a slice

CheckContext: 5 raw fields

project_dir skills lockfile_names excluded lockfile_skills

local_skill → uses 1, re-derives 3 paths

orphans → uses 3, re-derives 3 paths

skill_md → uses 1, re-parses frontmatter

invoke_only → uses 1, re-parses + re-reads

No check uses all five; each re-derives layout and re-parses frontmatter from (project_dir, name).

After — context yields per-skill facts

SkillFacts(layout, frontmatter, source)

checks read facts; no re-derivation, no re-parse

Layout (from #1) and parsed frontmatter computed once; checks consume, never re-compute.

Problem

CheckContext is a shallow raw-data bag; checks re-derive paths and re-parse frontmatter per run.

Solution

Deepen the context to hand each check a per-skill facts object (layout + parsed frontmatter).

Wins

  • locality: frontmatter parsed once per skill
  • checks shrink to pure classification
  • builds on #1's layout module
  • caveat: depends on #1 landing first

Top recommendation

Start with #1 — the skill layout module.

It is the deepest single change and the keystone for the rest. The on-disk layout of an installed skill is the one fact areg repeats most — six sites re-derive the same paths and symlink targets. Concentrating it passes the deletion test cleanly, and a SkillLayout module is exactly what #4 and #5 would hand to their callers. Land #1, then #2 and #3 in either order.
