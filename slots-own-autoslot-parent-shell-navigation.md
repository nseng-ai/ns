# Let Slots Own Autoslot Parent-Shell Navigation

## Goal and outcome

Remove Flow’s duplicate parent-shell directive filesystem implementation and make `ns flow autoslot` rely on the existing Slots navigation contract.

After this change:

- Flow invokes `ns slot checkout --current --no-clipboard --format json` without `--no-cd-directive`.
- Slots remains the sole owner of `NS_CD_DIRECTIVE_FILE` / `SLOT_CD_DIRECTIVE_FILE` resolution and directive-file writes.
- An installed `ns shell` wrapper continues to create the temporary directive file, set `NS_CD_DIRECTIVE_FILE` only for the child `ns` invocation, read the destination after a successful command, remove the file, and `cd` in the parent shell.
- Non-wrapper callers that set neither directive environment variable perform no directive write and no navigation.
- JSON stdout remains a valid machine envelope. The optional navigation side effect is enabled by the already-existing environment capability and can still be suppressed with `--no-cd-directive`.
- If Slot placement succeeds but the active directive cannot be written, checkout remains successful (exit 0), the structured result records the navigation failure, and autoslot emits a warning plus its existing manual navigation guidance. Placement is not rolled back and is not reclassified as a command failure.

## Context and discovered facts

- Current branch at planning time: `flow-autoslot-checkout-gateway-gating`; current commit: `b53feba4d` (`[cp] Route autoslot checkout through exec seam`). The worktree was clean.
- Flow’s implementation is in `ts/packages/capabilities/flow/src/autoslot/slot-checkout.ts`. It currently:
  - passes both `--no-clipboard` and `--no-cd-directive` to `ns slot checkout`;
  - owns `SLOT_CD_DIRECTIVE_FILE` / `NS_CD_DIRECTIVE_FILE` constants;
  - owns an `AutoslotDirectiveWriter` and a real filesystem adapter using `node:fs/promises.writeFile`;
  - writes the returned `worktreePath` itself after validating the Slots response.
- The high-level `SlotCheckoutGateway` was already removed in commit `b53feba4d`; checkout policy now runs over Flow’s injected command-exec seam. This plan must not recreate that Gateway.
- Slots already owns the canonical protocol in `ts/packages/capabilities/slots/src/core/shell/cd-directive.ts`:
  - `SLOT_CD_DIRECTIVE_FILE` takes precedence over `NS_CD_DIRECTIVE_FILE`;
  - absent/empty variables mean inactive;
  - the destination is written as UTF-8 with no added newline;
  - write outcomes are `inactive`, `written`, or `failed`.
- The canonical `ns shell` wrapper is generated by `renderCommandCdWrapperScript` in `ts/packages/capability-kit/src/kit/shell-support.ts`. It creates a temporary file, exports `NS_CD_DIRECTIVE_FILE` only to `command ns`, reads a non-empty file only after exit 0, deletes it, and changes the parent shell directory.
- Slots checkout already exposes `--no-cd-directive`; `checkoutRequestSchema.cdDirective` defaults to `true` in `ts/packages/capabilities/slots/src/lifecycle/operations/checkout.ts`.
- The production Slots ns-extension composition root currently sets `shouldWriteCdDirective: true` in `ts/packages/capabilities/slots/src/ns/slot-ns-command.ts`, independent of renderer/output format. Therefore JSON checkout can already honor the active wrapper; Flow is suppressing it explicitly. No new environment variable or new positive CLI flag is required.
- Test infrastructure currently drifts from production: `ts/packages/capabilities/slots/test/support/run-scenario.ts` sets `shouldWriteCdDirective` from `isClinkrHumanOutputInvocation(args)`, which makes machine-output scenarios behave differently from the production extension context.
- `prepareNavigation` currently awaits `writeCdDirectiveIfActive` but discards its result. Consequently a failed directive write is silently ignored and is unavailable in JSON output or Flow’s parser.
- Checkout, goto, and Graphite navigation all consume the shared `NavigationResultFields`; adding truthful directive status there requires coordinated schema/type/presentation updates, not a checkout-only ad hoc warning path.
- User decisions from grilling:
  - preserve and reuse the existing wrapper/environment protocol;
  - do not introduce a replacement navigation mechanism;
  - successful placement plus directive-write failure remains success with a visible warning.

## Implementation steps

### 1. Make Slots navigation results preserve directive outcomes

In `navigation-result.ts`, stop discarding `writeCdDirectiveIfActive(...)`.

Extend `NavigationResultFields` with one coherent, machine-readable representation of the existing `CdDirectiveResult`. Prefer a small discriminated status representation over several booleans that can form impossible states. A suitable shape is:

- `cdDirectiveStatus: "inactive" | "written" | "failed"`
- `cdDirectivePath: string | null`
- `cdDirectiveFailureDetail: string | null`

Maintain invariants:

- `inactive`: path may be null (no active wrapper) or non-null when explicitly disabled; failure detail is null.
- `written`: path is non-null; failure detail is null.
- `failed`: path is non-null; failure detail contains the filesystem failure.

If a nested discriminated object is cleaner and fits Clinkr/Zod conventions better, use it consistently instead of the flat example; do not create parallel representations. Preserve existing clipboard fields and semantics.

`prepareNavigation` must always return checkout/navigation facts even when the directive write fails. It must not throw for the existing expected `CdDirectiveResult.failed` outcome.

### 2. Propagate the canonical fields through Slots schemas and presentation

Update every schema/result type that mirrors `NavigationResultFields` so the machine envelope retains directive status instead of stripping it. At minimum this includes checkout, goto, and Graphite up/navigation surfaces; confirm the full list with a bounded grep for `NavigationResultFields`, `prepareNavigation`, and the existing clipboard fields.

Update `renderSlotNavigationSuccess` to render a warning line when `cdDirectiveStatus === "failed"`. The durable operation remains a success block and exit 0. Include enough detail to recover (the directive path and failure detail) without implying checkout failed.

Do not add a warning for `inactive`: absence of a wrapper is normal. Do not change clipboard behavior.

### 3. Make Slots scenario tests match the production composition root

Correct the scenario harness drift in `test/support/run-scenario.ts`. The production ns extension sets `shouldWriteCdDirective: true`; the harness should model that composition fact rather than infer permission from output format.

Because this shared correction may expose existing tests that encoded the old test-only “machine output never writes” assumption:

- update JSON navigation tests to assert the actual contract: with an active directive environment variable, JSON output may write; without one, no file exists and no side effect occurs;
- preserve explicit suppression coverage for `--no-cd-directive` on checkout;
- verify goto and Graphite navigation tests against their actual command options and production behavior rather than blanket-updating assertions.

Add checkout scenarios for:

1. `--format json` + active directive path + no opt-out writes the worktree path and returns `cdDirectiveStatus: "written"`;
2. the same call with `--no-cd-directive` leaves the file absent and reports inactive/disabled status;
3. no directive environment variable reports inactive and performs no write;
4. a nonexistent/unwritable directive parent leaves checkout at exit 0, returns status `failed` with path/detail, and retains successful placement data.

Use the existing temporary-directory helpers and fake-driven scenario infrastructure; do not add real-backend work to the default lane beyond the existing narrowly scoped temporary-file adapter tests.

### 4. Remove Flow’s duplicate writer and rely on the Slots result

In Flow’s `slot-checkout.ts`:

- remove the `node:fs/promises` import;
- remove Flow-owned directive environment constants, filesystem/writer interfaces, write-result type, factories, path resolver, and error normalization helper;
- remove `--no-cd-directive` from `buildSlotCheckoutArgs`, retaining `--no-clipboard` and `--format json`;
- extend `slotCheckoutTargetSchema` only with the Slots directive status fields Flow needs to classify navigation. Keep parsing at the external CLI boundary with Zod;
- have `checkoutSlot` call the injected exec seam, parse the machine envelope, and derive its warning list from Slots’ structured directive result;
- on `failed`, preserve the successful target and add Flow’s existing `cd-directive-write-failed` warning text using the Slots-provided path/detail;
- on `inactive` or `written`, return success without warnings.

Do not recreate a `SlotCheckoutGateway`. The injected command executor is the external seam; command selection, parsing, and warning policy remain Flow-owned logic above it.

In `autoslot.ts` and `api/index.ts`, remove `AutoslotDirectiveWriter` from `AutoslotFlowInput`, composition, imports, and exports. `createAutoslotFlow` should call `checkoutSlot(input.exec, { kind: "current" })` (or the final equivalent signature) and continue rendering warnings through `NsCommandIo`.

### 5. Rework Flow tests around the exec seam and Slots-owned evidence

Update unit tests so they fake only command execution:

- expected argv no longer contains `--no-cd-directive`;
- a successful Slots envelope with `cdDirectiveStatus: "written"` produces successful checkout without warnings;
- `inactive` also succeeds without warnings;
- a successful envelope with `failed` status produces the existing navigation warning while retaining the Slot target;
- command execution, malformed JSON/envelope, process/envelope mismatch, and Slots domain failure coverage remains intact;
- remove all fake filesystem and Flow directive-writer tests because that implementation no longer exists.

Update autoslot scenario fakes to include the new Slots checkout result fields. Preserve the user-visible scenario proving that directive failure does not fail autoslot and still prints the worktree and `ns slot co <branch>` guidance.

### 6. Align docs and Objective evidence

Document the final contract in Slots README language:

- the shell wrapper’s environment variable is the opt-in capability;
- JSON controls stdout representation, not whether an already-active parent-shell wrapper may navigate;
- `--no-cd-directive` disables that side effect;
- directive failure is reported but does not undo successful placement.

Update the Flow Slots Objective records listed above so a fresh reader does not conclude that Flow owns filesystem writes. Preserve historical commit/evidence references, but explicitly record the final remediation after `b53feba4d`.

## Risks, assumptions, and open questions

### Risks

- **Scenario-harness correction reveals broader drift.** Production currently enables directive handling independently of renderer, while tests infer it from human output. Correcting this may require expectation changes for goto and Graphite navigation. Treat those as contract reconciliation, not unrelated churn, and verify each command’s explicit options.
- **Schema stripping hides failure evidence.** If any Clinkr result schema is not updated, runtime objects may carry directive fields that disappear from JSON. Audit every navigation schema before considering the change complete.
- **Impossible status combinations.** Avoid independent booleans for written/skipped/failed unless the schema enforces invariants. Prefer one status discriminator plus nullable details.
- **Warning duplication.** Slots human presentation and Flow autoslot presentation are separate consumers. Ensure the Slots CLI does not emit unstructured stderr that corrupts or duplicates machine-mode handling; machine mode should carry warning evidence in the JSON data, and Flow should render it once.
- **Wrapper behavior depends on exit 0.** A directive-write failure must not make the successful checkout command nonzero, or the wrapper will intentionally refuse to navigate and Flow will misclassify successful placement as a boundary failure.

### Assumptions

- Automatic parent-shell navigation remains part of autoslot’s desired UX.
- Existing `NS_CD_DIRECTIVE_FILE` and compatibility `SLOT_CD_DIRECTIVE_FILE` names and precedence remain stable; no migration is needed.
- Breaking internal/private TypeScript result shapes is acceptable in this unreleased repository, but public package exports and documented machine output must still be updated coherently.
- No new positive `--cd-directive` option is needed because the active wrapper environment variable plus the existing negative opt-out provides the chosen contract.

### Open questions

No material requirement remains open. During implementation, exact field names for structured directive status may be adjusted to fit existing schema conventions, provided the representation is discriminated/coherent and carries status, path, and failure detail needed by Flow.
