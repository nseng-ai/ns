# How developer tools resolve a repository's trunk/default/base branch

**Accessed:** 2026-07-25\
**Scope:** Primary sources only: official documentation, APIs, and first-party source code. “Default branch” below means host/VCS metadata; “base branch” means the branch a particular operation targets. Those are often—but not always—the same thing.

## Executive conclusion

There is no universal Git-local answer to “what is this repository's trunk?” Git represents a **default per remote**, not one repository-wide trunk, and even that local `refs/remotes/<remote>/HEAD` symbolic ref is optional and cached. Representative tools therefore use one of four designs:

1. **Host-authoritative metadata at operation time** (GitHub CLI, GitLab CLI, Renovate, Dependabot);
2. **Explicit repository/tool configuration**, usually overriding a host default (Graphite, Changesets, Renovate, `gh`);
3. **A cached local remote bookmark/HEAD plus refresh or fallback rules** (Git, jj, Sapling); or
4. **No singular trunk abstraction**, requiring the caller to name a revision or working with multiple important/public heads (Git generally, Sapling in much of its UI).

For a tool that must work both online and offline, the strongest pattern is: **explicit override → remote-scoped local cached metadata → conventional fallback only when clearly labeled → actionable failure**. Store provenance (remote and discovery method), validate that the ref exists, and refresh/compare against host metadata when online. Do not silently treat `origin`, `main`, or the current branch as authoritative in fork/multi-remote repositories.

**Current ns implementation note (updated 2026-07-28):** ns intentionally chooses an offline subset
of that design. Its canonical Extension Kit repository-trunk module composes repository-root `[git]`
policy over neutral Git facts, then uses an explicit configured branch or the selected remote's
locally cached symbolic HEAD. It performs no host query, fetch, conventional fallback, or freshness
check. Identity resolution validates names, derives the local and selected remote-tracking ref names,
and records whether the branch was configured or came from cached remote HEAD; it does not require
those refs to exist. Each consuming workflow separately validates the exact local and/or
remote-tracking refs needed for its operation and reports workflow-specific recovery. Graphite
topology trunk remains a separate concept. This implementation note postdates the primary-source
survey below and does not change that research's provenance or conclusions.

## Comparison

| Tool                              | Resolution model                                                                                                                                                                                                                                                                                                                                        | Offline behavior                                                                                                                                                                  | Forks, multiple remotes, and drift                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Git**                           | Avoids a repository-wide trunk. A remote can advertise symbolic `HEAD`; clone uses it to choose the initial branch. Locally, optional `refs/remotes/<name>/HEAD` names that remote's default. `git remote set-head <name> --auto` queries and updates it; an explicit branch can set it without discovery.                                              | The cached remote-tracking symbolic ref is usable offline if present. It is not required and does not self-refresh.                                                               | The concept is explicitly **per remote**. `set-head --auto` requires the corresponding remote-tracking branch to have been fetched, which provides existence validation but not freshness after the server default changes.                                                                                                                                                                  |
| **GitHub API / `gh pr create`**   | GitHub exposes repository `default_branch` / GraphQL `defaultBranchRef`. `gh pr create` uses `--base`, then local `branch.<current>.gh-merge-base`, then the **base repository's** API-provided default branch.                                                                                                                                         | Default discovery requires GitHub access (unless an explicit `--base` or local override supplies the answer); it does not use local `origin/HEAD` as its documented fallback.     | `gh` resolves a base repository separately from the push/head repository, so fork PRs target upstream metadata rather than the fork's default. The explicit per-branch override supports workflows whose base differs from the host default.                                                                                                                                                 |
| **GitLab API / `glab mr create`** | The Projects API returns `default_branch`. `glab` accepts `--target-branch`; otherwise current source code checks GitLab project target-branch rules for the source branch and falls back to the target project's `DefaultBranch`.                                                                                                                      | Automatic selection is API-dependent. An explicit target can be supplied, but MR creation still inherently needs the host.                                                        | Resolution is against the target project, not merely a local remote name. `glab` validates the selected target through the Commits API before creation. Project target-branch rules allow branch-specific bases rather than forcing one trunk.                                                                                                                                               |
| **Graphite**                      | Explicit Graphite repository configuration: `gt init --trunk <name>` selects or changes trunk; current Graphite also supports multiple configured trunks and an optional target trunk.                                                                                                                                                                  | Configured local trunk remains available offline for local topology operations. Sync/submit freshness checks require the remote.                                                  | `gt submit` normally blocks an out-of-sync trunk; `--ignore-out-of-sync-trunk` is an explicit unsafe escape hatch. `--target-trunk` defaults through configured target-trunk mapping, then local trunk. This is strong validation, but configuration can drift until a remote operation checks it.                                                                                           |
| **Renovate**                      | Platform adapters read authoritative host metadata (`defaultBranchRef.name` on GitHub, `default_branch` on GitLab). By default Renovate processes the repository default branch; `baseBranchPatterns` explicitly selects one or many bases and supports `$default`. Config itself is normally read from the default branch.                             | Normal hosted/platform operation is not an offline resolver. A checkout's local remote HEAD is not the authority in these adapters.                                               | Multiple base branches are first-class. Renovate separates fixed `defaultBranch` from configured base branches. Its GitHub adapter also detects a fork whose default differs, creates/aligns the parent default branch in the fork, and sets it as fork default—active reconciliation rather than trusting stale local state. Empty repositories without host default metadata are rejected. |
| **Dependabot**                    | GitHub-owned service metadata is authoritative. Without `target-branch`, version updates target the repository default; explicit `target-branch` changes version-update behavior. Security updates always target the repository default.                                                                                                                | No meaningful offline mode; this is a hosted service.                                                                                                                             | Explicit configuration can diverge from default for version updates, but not security updates. A host default rename therefore automatically changes the security-update base and the implicit version-update base.                                                                                                                                                                          |
| **Changesets**                    | Explicit repository config: `baseBranch` is the comparison base and should be the branch changes merge into. The shipped example/default is `master`; it does not claim to discover host metadata or local remote HEAD.                                                                                                                                 | Fully deterministic offline once configured and refs are present.                                                                                                                 | Simple and reproducible, but conventional default/config can drift after branch renames. Correctness depends on maintainers updating config and ensuring the named ref exists locally.                                                                                                                                                                                                       |
| **Jujutsu (`jj`)**                | `trunk()` is a configurable revset alias. At repository initialization it resolves the default bookmark of the default remote, then `upstream` or `origin`; if unresolved, global defaults try `main`, `master`, and `trunk` on those remotes, choosing the newest candidate. If none exists it resolves to `root()`. Users can override it explicitly. | Resolution uses imported remote bookmarks and repository config, so it remains usable offline but can be stale until fetch.                                                       | Remote priority and conventional fallback are explicit. Ambiguity is handled by “newest,” which is deterministic but potentially surprising. Docs require overrides to resolve to exactly one commit. Falling all the way to `root()` avoids hard failure but can conceal missing trunk metadata if callers do not inspect it.                                                               |
| **Sapling (`sl`)**                | Sapling's common model emphasizes remote bookmarks, public/draft commits, and a smartlog that can show `main` **and other configurable important branches**, rather than requiring every operation to resolve one trunk. For Git repos, remote bookmarks correspond to Git branches.                                                                    | Remote bookmarks are immutable local representations of server bookmark positions **as of the last pull**, so graph/UI operations work offline with explicit staleness semantics. | This naturally represents multiple important heads. The tradeoff is that callers needing a release/merge base still name/configure a bookmark; Sapling does not provide evidence here of a universal host-derived trunk equivalent.                                                                                                                                                          |

## Design implications

- **Separate identity from freshness.** “The configured base is `main`” and “local `upstream/main` matches the server” are different facts. Graphite's submit guard models this well.
- **Make the remote part of the value.** Git, jj, and Sapling all expose why branch name alone is insufficient. In a fork, `origin/main` and `upstream/main` can both exist and differ; GitHub/GitLab tools intentionally resolve the target/base repository.
- **Prefer host metadata when the operation is host-defined.** PR/MR targets, hosted dependency updates, and default-branch policy belong to GitHub/GitLab and should use their API fields, not infer from a checkout.
- **Prefer explicit config when semantics are tool-defined.** Changesets' comparison base, Renovate's multiple bases, and `gh`'s branch-specific merge base may intentionally differ from the host default.
- **Use local remote HEAD only as a cache, never as an unquestioned singleton.** It may be absent, stale, or attached to the wrong remote. Refresh with the remote protocol/API when online and report the source when offline.
- **Validate at boundaries.** Check that the selected ref exists locally before graph operations and remotely before creating a PR/MR; report mismatch rather than silently switching to `main`/`master`. Conventional fallback is most defensible at initialization (jj) and least defensible for destructive or publishing operations.

## Appendix: where developer tools place repository metadata

**Short answer:** yes, but it is not the dominant convention. Besides Graphite, Git LFS and git-annex are confirmed examples of tools keeping substantial private state under the shared Git directory. Other common tools prefer Git's standard config or hook surfaces, or a worktree-root directory. The distinction matters because in a linked worktree `git rev-parse --git-dir` identifies the per-worktree administrative directory (typically `<common>/worktrees/<id>`), while `--git-common-dir` identifies storage shared by every linked worktree.

| Tool                                    | Placement and evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Linked-worktree consequence                                                                                                                                                                                                                                                                                                  |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Git LFS**                             | **(a), private shared directory.** Its default `LFSStorageDir` is `.git/lfs`. Current code first obtains `--git-dir`, then explicitly follows that directory's `commondir` file before placing `lfs` alongside the shared Git object directory. This is common-dir semantics implemented manually, not merely a hardcoded `.git` and not, for this path, a direct call to `--git-common-dir`. (`GitCommonDir()` also exists for other operations.)                                                                   | Linked worktrees share one LFS object store under the common directory rather than creating `<common>/worktrees/<id>/lfs`. `lfs.storage` can override the default.                                                                                                                                                           |
| **git-annex**                           | **(a) plus (b).** Private content and journals live under `.git/annex`; shared logs are committed on the standard `git-annex` branch, and identity/config such as `annex.uuid` uses Git config. Current source derives the annex path from its resolved local Git directory. For linked worktrees it reads `commondir` itself and makes the linked worktree's `annex` path point to the main repository's annex store. Thus it achieves common-store behavior, but not by invoking `git rev-parse --git-common-dir`. | Worktrees share annex objects and Git config/UUID. This support is invasive: on symlink-capable systems git-annex documents replacing the linked worktree's `.git` file with a symlink and adding an `annex` link. It is therefore precedent for shared private storage, but not for a simple portable common-dir API alone. |
| **pre-commit**                          | **(b), standard Git hooks.** Installation calls `git rev-parse --git-common-dir` (falling back to `--git-dir` only for Git older than 2.5) and writes `hooks/<hook-type>` there. This is the clearest direct, worktree-aware consumer of the common-dir API in the sample, but `hooks/` is Git's standard hook surface rather than a private pre-commit directory.                                                                                                                                                   | One installed hook is shared by all linked worktrees. This matches Git's repository-wide hooks model; it does not create per-worktree pre-commit state.                                                                                                                                                                      |
| **Gerrit `commit-msg` hook**            | **(b), standard Git hook, but documented with a hardcoded worktree-root path.** Gerrit's installation commands copy to `<checkout>/.git/hooks/commit-msg`; they do not resolve `--git-dir`, `--git-common-dir`, `git rev-parse --git-path hooks`, or `core.hooksPath`. Git itself says the default is `$GIT_DIR/hooks`, overridable by `core.hooksPath`.                                                                                                                                                             | The documented command fails for an ordinary linked worktree because its `.git` is a file, and it ignores a custom hooks path. Gerrit supplies the hook but does not provide worktree-aware placement instructions.                                                                                                          |
| **GitHub CLI (`gh`)**                   | **(b), Git config; no private Git-directory state found for this feature.** `gh pr create` documents and reads `branch.<name>.gh-merge-base` through `git config`.                                                                                                                                                                                                                                                                                                                                                   | Ordinary local config is in the shared repository config by default, so linked worktrees see the same value. Git's optional `extensions.worktreeConfig` can make selected config worktree-specific; `gh` delegates that policy to Git.                                                                                       |
| **Git Town**                            | **(b), Git config.** Official docs store `git-town.main-branch` and related repository metadata with `git config` (or optionally global config). Current source does call `git rev-parse --absolute-git-dir`, but only to inspect standard per-worktree operation state such as `SQUASH_MSG` and rebase directories—not to place Git Town's own metadata.                                                                                                                                                            | Repository-local Git Town settings are shared by default. Its use of `--absolute-git-dir` for merge/rebase state is correctly per-worktree and is not evidence for private common-dir storage.                                                                                                                               |
| **Jujutsu (`jj`) colocated repository** | **(c), worktree-root metadata.** A colocated workspace places `.jj/` beside `.git/`; `.jj/repo/` holds repository state and `.jj/working_copy/` holds workspace state. Additional jj workspaces each have a `.jj/` linked to the main repo. jj does not put its private state below Git's common directory.                                                                                                                                                                                                          | Git worktree identity does not determine jj's metadata location. jj has its own explicit repository/workspace sharing model, so treating `.jj` as if it were common-Git-dir state would conflate the two models.                                                                                                             |

The representative pattern is therefore: use a **private common-dir child** for large repository-shared local stores (LFS, annex); use **Git config, refs, or hooks** when Git already owns the namespace (gh, Git Town, annex logs/config, pre-commit); and use a **root sibling directory** when the tool has its own repository/workspace model (jj). A new private file intended to be shared across linked worktrees should resolve the common directory explicitly (or equivalently and carefully follow `commondir`), not append to `--git-dir` or `<worktree>/.git`. Conversely, operation state associated with one checkout belongs under `--git-dir`, as Git Town's rebase checks illustrate.
