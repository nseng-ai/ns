- Before editing, classify feedback groups as AUTO, STEER, or DEFER.
- AUTO is allowed when the agent can confidently make a bounded, reviewable fix without a product/design decision. AUTO may include multi-file edits, new or shared helpers, dependency additions that satisfy repo layering/package policy, schema/type source-of-truth consolidation, localized control-flow refactors, and deciding that a comment is already fixed or stale against the current repo state.
- STEER is required when the change would alter user-visible behavior, public API/CLI contracts, data persistence semantics, or compatibility promises; crosses or redefines ownership/layering boundaries; has an uncertain or failed dependency/layering check; requires choosing between materially different designs; is broad enough that a human would reasonably want to choose the slice/order first; conflicts with repo rules, active objective orientation, or other review feedback; or cannot be validated by the agent.
- Grouping feedback is for triage clarity, not automatic implementation permission. A grouped theme may still be AUTO only when the planned implementation remains bounded and reviewable; do not convert many small comments into a surprisingly broad refactor without a checkpoint.
- If the AUTO plan becomes broad — for example, many files, new shared abstractions, schema/type consolidation, or closing many threads — do not stop by default, but first produce a short checkpoint unless the user explicitly asked for hands-off execution: groups to fix automatically, why they are still bounded, what will be left for steering, and the validation/thread-closure plan. Proceed after confirmation or explicit “continue automatically.”
- For AUTO fixes, edit the minimal files needed and run appropriate validation.
- Close review threads only for feedback directly addressed by the implemented and validated change, or confidently verified as already fixed/stale against the current repo state, using `ns address exec close-review-threads --thread-ids-json '{"threadIds":["<THREAD_ID>"]}' --format json`; include `--body <BODY>` when a reply is useful. Do not close threads merely because a broad related refactor might have made them stale. Use single-thread `reply-review-thread` and `resolve-review-thread` primitives only for one-offs, and do not use raw `gh api graphql` for review-thread resolve/reply mutations.
