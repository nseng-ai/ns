# dev-workbr-create

Stash a plan file into **branch memory** on a new branch without ever
checking that branch out. The current worktree stays put; a companion
skill (`dev-workbr-impl`) picks up the plan later from a fresh worktree
opened on the new branch.

## Goal

Given a plan file (from conversation context or an explicit path), produce:

1. a new branch whose name is a kebab-case slug summarizing the plan,
   pointing at the current `HEAD`
2. a brmem entry at `refs/brmem/brs/<slug>:plan.md` containing the plan
   verbatim
3. a report telling the user how to open a worktree on the new branch
   and run `dev-workbr-impl` to begin work

Responsibility ends at the brmem commit. The working tree is never
modified. No push, no `gt submit`.

## Core rules

- **Copy the plan verbatim.** Do not regenerate, summarize, rewrite, or
  append a footer. Brmem entries are metadata attached to the branch,
  not in-tree artifacts — there is nothing to self-destruct.
- **Slug is generated by the model** from the plan's title + intent. No
  slug utility, no script — the model produces it directly per the
  rules below.
- **Bare slug branch name.** No `plan/` prefix, no `workbr/` prefix. The
  slug is the branch name and the brmem key.
- **Never touch the working tree.** No `git add`, no `git checkout`, no
  file writes at the repo root. The `Write` tool is used only to write
  the harness-owned session-plan file during plan-mode exit.
- **No clean-tree requirement.** Because the working tree is never
  touched, it's fine for it to be dirty. The user can keep working on
  whatever they were working on.
- **Never push.** Never `gt submit`. The skill ends at the brmem commit.
- **Exit plan mode before running.** If the current harness exposes
  plan mode on entry, the skill's first action is to resolve the plan
  file, generate the slug, write a short session-plan to the
  harness-owned session plan path, and call `ExitPlanMode`. All steps
  that run `git branch` or `brmem put` require plan mode to be off.
- **Use raw `git branch`, not `gt create`.** `gt create` always checks
  out the new branch — that's the behavior we're explicitly avoiding.
  Raw `git branch <slug> HEAD` only updates refs. (The branch won't be
  Graphite-tracked; `gt track` can run later inside the new worktree
  if the user wants to stack on top.)

## Workflow

### 1. Exit plan mode (if active)

If the current session is in a harness-managed plan mode — meaning the
system context exposes both that plan mode is active and a writable
session-plan path — the skill cannot run its `git branch` / `brmem
put` steps until plan mode has been exited.

Do, in order:

1. Run step 2 below to resolve the source plan file the skill is about
   to stash (call its path `<source-plan>`).
2. Generate the slug per step 3 below.
3. Use the `Write` tool to write a short session-plan to the
   harness-provided session-plan path (this is the session's plan file,
   not the source plan). The session-plan should describe exactly what
   the skill is about to do, e.g.:

   ```
   # Stash <source-plan> on a new branch via brmem

   Run `dev-workbr-create` to:
   - Create a new branch `<slug>` pointing at the current HEAD via
     `git branch <slug> HEAD` (no checkout).
   - Stash `<source-plan>` verbatim into
     `refs/brmem/brs/<slug>:plan.md` via `brmem put`.

   The current worktree is not modified. No push, no `gt submit`.
   ```

4. Call `ExitPlanMode`. It reads the session-plan file you just wrote
   and requests user approval.
5. After approval, continue with step 4 (pre-flight checks). Steps 2
   and 3 have already run inside this step and do not need to be
   re-run.

If plan mode is **not** active, skip this step entirely and start at
step 2.

### 2. Resolve the plan file (context-first)

Try in order; stop at the first that succeeds:

1. **Explicit argument.** If the user passed a path, use it. Error if
   the file doesn't exist or isn't readable.
2. **Conversation context.** Scan recent context for a plan file path.
   Harnesses that support plan mode often surface one in a system
   reminder or equivalent session metadata. If exactly one such path
   appears recently, use it. If multiple distinct paths appear, pick
   the most recent reference and call out that choice in the report.
3. **Filesystem fallback.** If recent context identified a concrete
   plan directory, list its markdown files newest-first and take the
   first one (for example, `ls -t ~/.claude/plans/*.md | head -1` in
   Claude Code).

If all three fail, abort with a clear error explaining what was tried.

### 3. Generate the slug

Read the full plan content, then produce a kebab-case slug from the
title + intent:

- lowercase ASCII, hyphen-separated, ≤50 characters
- leads with a verb when natural (`add-`, `refactor-`, `migrate-`,
  `rename-`)
- no `-plan` suffix — `plan.md` inside brmem already signals that
- describes the _change_, not the document (e.g.
  `add-workbr-create-skill`, not `plan-for-workbr-stasher`)

The slug doubles as the branch name and the brmem ref key.

### 4. Pre-flight checks

Run these and abort on the first failure:

- `git rev-parse --show-toplevel` → must succeed. Error if not in a
  git repo.
- `git rev-parse --verify refs/heads/<slug>` — must **fail**
  (exit-code non-zero). If the ref exists, abort and ask the user to
  pick a different slug or delete the stale branch.
- `git rev-parse --verify refs/brmem/brs/<slug>` — must **fail**. If
  the brmem ref exists (rare — typically indicates a half-created
  workbr from a prior run), abort.
- `git rev-parse HEAD` → capture the start-point SHA for the report.
  Abort on detached HEAD.
- **No clean-tree check.** The working tree is explicitly allowed to
  be dirty; we never modify it.

### 5. Create the branch without checkout

```
git branch <slug> HEAD
```

- This is `git branch`, not `gt create`. `gt create` always checks out
  the new branch, which is exactly the behavior we're avoiding.
- The new branch points at the same commit as the current worktree's
  `HEAD`.
- The worktree stays on its current branch; nothing in the working
  tree changes.

### 6. Stash the plan via brmem

```
brmem put <source-plan-path> --branch <slug> --path plan.md
```

- `<source-plan-path>` is the plan file resolved in step 2.
- `--branch <slug>` targets the branch created in step 5.
- `--path plan.md` fixes the in-memory filename to a predictable key
  so the companion `dev-workbr-impl` skill can fetch it with
  `brmem get plan.md`.
- Contents are written **verbatim** — no footer, no rewriting.
- Capture the ref path (`refs/brmem/brs/<encoded-slug>`) and commit
  SHA returned by `brmem put` for the report.

### 7. Report

Print a short summary to the user:

- branch name created + start-point SHA (from step 4)
- brmem ref path and commit SHA (from step 6)
- source plan file path (so the user can spot a wrong
  context-resolution)
- next-step hint:

  ```
  Open a worktree on this branch:
    slot checkout <slug>
  Then from the new worktree, run:
    /dev-workbr-impl
  to pull the plan from brmem and begin implementing.
  ```

## Edge cases

- **Not in a git repo** → abort with guidance.
- **Detached HEAD** → abort with guidance; brmem keys are branch
  names, so we need one.
- **Branch `<slug>` already exists** → abort; do not clobber. Ask the
  user to pick a different slug or delete the stale branch first.
- **brmem ref for `<slug>` already exists** → abort; same rationale.
- **Plan file very small (<20 lines)** → warn but proceed.
- **Multiple plan paths in context** → pick the most recent
  reference, name the choice in the report so the user can re-run
  with an explicit path if wrong.
- **Working tree dirty** → fine; we never touch it. This is a
  headline benefit of this skill over `dev-plan-to-branch`.

## Anti-patterns

- Checking out the new branch (via `gt create`, `git checkout -b`,
  `git switch -c`, etc.) — the whole point is to decouple "capture
  the plan" from "work on the plan".
- Writing `plan-<slug>.md` into the working tree. That's what the
  sibling `dev-plan-to-branch` skill does. This variant keeps the
  plan out of the tree on purpose.
- Adding a self-destruct footer. Brmem entries are metadata, not
  tree contents — they don't need one and the implementer expects
  verbatim content.
- Running `gt track` or `gt submit` — the branch is intentionally
  loose. Any Graphite tracking happens later, in the new worktree,
  at the user's discretion.
- Using `git add` or otherwise staging files. This skill never writes
  to the repo root.
- Regenerating, summarizing, or rewriting the plan.
