# pr-make-accountable

The engineer whose name is on a PR must be able to explain it. This skill runs
an interview over one PR: you build the understanding from the evidence. You
then interview the engineer to get enough shared understanding to co-author
this template:

```markdown
<!-- ns-pr-authored:begin -->

## Why

Why is this change needed? What problem does it solve?

## What changed

High-level orientation bullets (what and where), then the design decisions,
tradeoffs, or limitations necessary to understand the implementation — each
explained from zero.

## Reviewer focus (optional)

Anything you'd especially like reviewers to pay attention to.

<!-- ns-pr-authored:end -->
```

Ground truth in the PR should not contradict the engineer's understanding of their
own PR. Additionally you may need to ask the engineer about intent and context not knowable
from the PR contents to gain sufficient understanding to co-author the PR summary.

Three accountability questions drive the session and structure the wrap-up:

1. Does the PR communciate the rationale, goals, and context of the change?
2. Is the PR presented and constructed to be consumable by a human reviewer?

## Scope and boundaries

- **One PR.** Default target is the current branch's PR; accept an explicit
  number or URL. Use `gh` for PR metadata and the body write, read-only local
  `git` for the diff.
- **Requires an existing PR.** If none exists, stop and tell the user to
  submit first (for example with `ns flow submit`).
- **The only write is the PR body**, always via `gh pr edit <n> --body-file
  <tmpfile>` — never an inline body. Commits, branches, labels, reviewers, and
  repo files stay untouched.
- **Consumability findings are advise-only.** Report construction problems;
  the engineer decides what to do with them.

## Phase 1 — Build inventory

Build your own inventory of the PR before asking the engineer anything:

- `gh pr view <n> --json title,body,url,number,baseRefName,headRefName,headRefOid,additions,deletions,changedFiles,commits`
- Confirm the local checkout reflects the PR: the checked-out branch is
  `headRefName` and local HEAD equals `headRefOid` (fetch first if needed). If
  they diverge, stop and tell the user to sync before continuing.
- Read the diff locally: `git diff --stat $(git merge-base HEAD
  origin/<baseRefName>)...HEAD` for the shape, then `git diff` / `git show`
  per file for depth (for very large diffs, sample per-file rather than
  truncating blindly).
- Note whether the existing body already contains an
  `<!-- ns-pr-authored:begin -->` region (re-run) and/or an
  `<!-- ns-pr-description:begin` managed region (autogenerated part).

The phase 1 analysis is complete when have developed your own inventory: the problem this PR appears to be solving , the conceptual shape of the change, design decisions and tradeoffs made in\
the PR, known limitations, and the risky or subtle spots a reviewer would stumble on.

## Phase 2 — Interview to build shared understanding

Interview the engineer one question at a time.

Present a summary inventory of changes to the user.

You should always start with: "Why is this change needed? What problem does it solve?"

**Ask in plain prose, expecting free-text answers.**

Pose one open-ended question per turn as an ordinary assistant
message and wait for the engineer's freeform reply.

- **Scale depth to the PR's decision surface.** A trivial fix earns one or two
  probes; a large feature earns a full walk of the decisions, tradeoffs, and
  limitations.
- **Ask only about the PR's final state.** Every question must help explain or
  review what the PR will contain when merged: its resulting behavior,
  rationale, design, tradeoffs, limitations, or reviewer-relevant risks. Do not
  interview the engineer about transient implementation states, intermediate bugs,
  abandoned steps, or the sequence used to reach the final diff. Such history
  matters only when it directly explains a decision or limitation that remains
  in the final state.
- **Never ask about lookupable content.** If a correct answer is
  verbatim-recoverable from a file in the diff or the PR body (an inventory of
  what was added, a roadmap's remaining-work list, a config's field values), do
  not ask it — the engineer can always re-read the artifact. Ask instead why
  the artifact says what it says: the scoping choice, the alternative rejected,
  what breaks if it were different.
- Probe *why* the change is needed, *what* conceptually changed, which
  tradeoffs were taken and what was rejected.
- When an answer is wrong or hedged, correct it with concrete evidence
  (file/line), then ask follow-ups in that area until the engineer's mental
  model is clear and does not contradict the change inventory.
- Correct only errors that would mislead a reviewer or reveal a wrong mental
  model. Do not "refine" a substantively correct answer with inventory details
  from your understanding; incomplete-but-right is a pass, not a repair.

The exam is complete when every topic carries a verdict:
**understood**, **repaired**, or **unresolved**. That record gates Phase 3.

## Phase 3 — Gated authored section

Draft the authored section only from the shared understanding reached with the PR author. It must be a concise, self-contained narrative for a cold reviewer:

- explain the reason and problem;
- open `## What changed` with a compact high-level map of major behavior changes and where they live;
- explain design decisions, rejected alternatives, and tradeoffs needed to understand the final state;
- state accepted risks and limitations, plus optional reviewer focus.

Do not produce a file-by-file mechanical inventory. The authored section should be commensurate with the PR's decision surface, not its line count. Explain risks and judgment calls from zero: state any underlying mechanism before the conclusion that depends on it.

Immediately before drafting, **read [`caveman.md`](caveman.md)**. Then:

1. Draft from the shared understanding.
2. Run a separate **lite** rewrite that removes filler, hedging, pleasantries, and repetition while retaining articles, full professional sentences, exact technical terms, paths, commands, code, and error strings.
3. Audit the transformed draft before presenting it. Reject dropped articles or fragments characteristic of full/ultra compression. Also reject unchanged verbose prose that shows no lite pass.
4. Show the complete transformed authored region to the engineer and wait for explicit approval or edits before writing.

Lite is a one-time drafting transformation, not a session mode. Omit the `## Reviewer focus (optional)` heading entirely when there is nothing to say.

### Writing the body

Before assembling anything, validate the existing body structurally. It may contain exactly zero or one complete `ns-pr-authored` region and exactly zero or one complete `ns-pr-description` managed region. If either marker pair is duplicate, nested, reversed, or incomplete, **stop without editing GitHub** and report the malformed body; do not guess or use heuristic deletion.

After approval:

1. Remove the old complete authored region if present, then normalize the approved complete authored region to the beginning of the body.
2. Remove exactly the complete `<!-- ns-pr-description:begin ... -->` through `<!-- ns-pr-description:end -->` managed region. Remove only its surrounding separator blank lines needed to leave clean Markdown. If no managed region exists, removal is a no-op.
3. Preserve every other human-authored byte and its order as far as newline normalization permits. Never delete legacy or unmarked text merely because it resembles generated prose.
4. Perform exactly one write with `gh pr edit <n> --body-file <tmpfile>`.
5. Read the body back and verify that the authored region is first, exactly one authored region remains, both managed markers are absent, and unrelated human text remains. Report failure rather than making a second speculative write.

The `ns-pr-authored` markers are skill-owned. Ordinary `ns flow submit` will not recreate a managed region on an existing PR. Later `ns flow submit --regenerate-descriptions` or `ns flow regenerate-pr` may intentionally recreate one while preserving text outside that managed region.

## Phase 4 — Consumability report

After the body is updated, give an advise-only verdict covering all four axes:

- **Size and cohesion** — is the diff reviewably sized and semantically
  focused, or should it have been split?
- **Title honesty** — does the title match what the diff actually does?
- **Narrative** — do the commits/body let a reviewer build the right model
  before reading code?
- **Focus** — did the exam reveal spots that deserve a reviewer's extra
  attention, and are they now in `## Reviewer focus`?

Report findings with concrete recommendations; the engineer executes any
restructuring.

## Wrap-up

End with: the PR URL, a one-line status per accountability question (understood
/ communicated / consumable), any unresolved answer-key topics, and any doc
gaps the exam exposed (flag only — writing docs is not part of this skill).
