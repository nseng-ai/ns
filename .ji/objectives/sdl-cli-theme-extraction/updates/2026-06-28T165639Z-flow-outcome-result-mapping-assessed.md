# Flow Outcome Result Mapping Assessed

## Summary

Assessed outcome/result discriminator mapping across the finite Flow command surfaces and found no production refactor worth making in this slice. The current boundary already matches the Objective: `@sdl/cli-theme` owns the generic finite result-block grammar (`success` / `failure` / `refusal`, headline/body/guidance/cwd layout), while Flow owns command/domain mapping, subprocess transcript interpretation, refusal classification, warning emission, and stdout/stderr/exit routing.

Evidence matrix:

| Flow command           | Outcome facts inspected                                                                                                                                                            | Renderer boundary                                                                                                                                                                                                         | Routing / policy notes                                                                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `autobranch`           | `AutobranchCheckpointResult`: success with summary/warnings, pending-worktree probe failure, clean-worktree guardrail, dirty-worktree `AutobranchFlowOutcome` `refusal`/`failure`. | Success and clean-worktree refusal call `renderResultBlock` directly; probe failures use Flow-local `renderPendingWorktreeFailure`; dirty-worktree flow failures use Flow-local `renderAutobranchFailureResultBlock`.     | Warnings are emitted to stderr before an `ok(...)` success; clean-worktree and flow refusals are `failed(..., 1)` warn refusals; `AutobranchFlowOutcome` stays in `@sdl/autobranch`/Flow, not the theme. |
| `branch-latest-commit` | Pending-worktree probe failures, dirty-worktree guardrail, latest-commit eligibility/transaction `AutobranchFlowOutcome`, success summary/warnings.                                | Probe failures use `renderPendingWorktreeFailure`; dirty-worktree refusal uses `renderGitResultBlock`; latest-commit failures/refusals use `renderAutobranchFailureResultBlock`; success uses direct `renderResultBlock`. | Eligibility guardrails render `refusal` through Flow-local classification; real transaction/probe failures render `failure`; warnings remain command-edge stderr before success.                         |
| `pull-trunk`           | `TrunkPullOutcome`: `success`, `trunk-command-failed`, `trunk-empty`, `worktree-list-failed`, `update-failed`.                                                                     | All outcomes render through Flow-local `renderGitResultBlock` because each carries git/Graphite command, cwd, exit, and transcript facts.                                                                                 | Command maps the CCC trunk-pull outcome to success vs failure locally, then chooses `ok(block)` only for success and `failed(block)` otherwise. No refusal or warning abstraction is present.            |
| `push`                 | Status inspection failure, dirty-worktree refusal, push success, push failure.                                                                                                     | All outcomes render through Flow-local `renderGitResultBlock`; the renderer mines `ExecResult` stdout/stderr for failure cause markers and formats command/cwd/exit/transcript plumbing.                                  | Dirty worktree is a warn refusal and does not run `git push`; status/push failures are real failures; routing stays at `ok(...)`/`failed(...)` in the command.                                           |
| `regenerate-pr`        | Prepared PR description failure with optional exit code, missing confirmation channel, declined confirmation, GitHub edit failure, success.                                        | Domain-authored messages use `renderResultBlockFromMessage`; confirmation refusals/edit failure/success use direct `renderResultBlock`.                                                                                   | Confirmation availability/decline are command-specific guardrail refusals; PR prep can supply an exit code; no subprocess transcript mining belongs in the theme.                                        |

Comparator evidence stayed consistent: CCC `autoslot` and `land` keep local facades (`AutoslotResultKind`, `LandResultKind`) over the same theme layout because notify levels, exit-code flipping, Pi ANSI-free stream paths, and domain facts are not theme concepts.

Decision: keep Flow outcome mapping local with no code change. Do not promote `AutobranchFlowOutcome`, `TrunkPullOutcome`, PR regeneration guardrails, git/Graphite `ExecResult` transcript cause mining, warning routing, or `ok(...)`/`failed(...)` decisions into `@sdl/cli-theme`. No new Flow-local helper was added because the live helpers already own real Flow concepts and no repeated domain-free mapping beyond `ResultBlockKind` was found.

## Objective Impact

- Completed the roadmap row for outcome/result discriminator to result-block mapping.
- Updated the Objective open questions to record this decision and leave only the remaining non-Slot consolidation candidates open.
- Reinforced the package boundary: `@sdl/cli-theme` remains a pure presentation grammar package; Flow and CCC command faces own domain result discrimination, refusal/failure policy, warnings, transcripts, and exit/routing mechanics.

## Follow-Ups

- Continue the remaining conservative assessments: success-with-warnings rendering, caps-resolution helper placement, table rendering, and status-to-intent mapping helpers.
- Treat success-with-warnings as the next likely adjacent row if warning routing continues to appear duplicated, but keep routing/severity policy out of `@sdl/cli-theme` unless a domain-free visual primitive emerges.
